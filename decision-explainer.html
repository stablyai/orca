The PR panel was talking to the other machine.

Ship it. When one project is open on two machines at once, this branch makes every check, comment, PR refresh and PR badge change go to the machine that actually owns the workspace you are looking at — instead of silently using whichever copy the app happened to find first.

Ship
Correctness fix inside existing routing. No new screens, no new settings, no backend API redesign. The wrong answers now become a clear “can’t load” instead of confidently wrong data.
One-line problem

Opening a check, a comment, or a PR refresh for a workspace on a remote machine could load and write to the local copy of the same project — showing green checks for a branch that failed, and posting your reply on a PR you weren’t looking at.

One-line fix

Every PR, check, comment and badge action now carries the machine that owns the workspace and is verified against it — and when two machines could both match, the app refuses with a plain message instead of guessing.

2 Scope boundaries
What this change DOES What this change does NOT touch
  • Checks & check logs load from the machine the workspace lives on, not the first project row with a matching name or folder.
  • Comment replies, reactions and thread resolution post to the same machine whose PR you have open.
  • PR card and badge refreshes after push / pull / sync refresh the copy you are actually on.
  • Check detail tabs opened on a remote machine get their own tab and stay there.
  • AI review requests are refused when the project and workspace disagree about which machine owns them.
  • Unlink / relink of a PR badge is applied only to the workspace and moment it was captured in.
  • No visual redesign. No layout, color, typography or component changes — only hooks that pass along which machine owns the request.
  • No new UI controls. No new buttons, menus, settings, toggles or shortcuts.
  • No change to how git push / pull / fetch actually run, or to git remotes, providers or PR fetching itself.
  • No single-machine behavior change. If a project exists on one machine only, every code path resolves the same as before.
  • No migration step. Existing saved workspaces, caches and tab state keep working; only newly opened remote check tabs get a machine-scoped ID.
  • No mobile or CLI changes. Remote and folder-workspace cases are exercised, but their surfaces are unchanged.

5 Why the old check failed
Question the old code asked The superficial pass — why it passed anyway Missing question this PR adds
“Is there a workspace with this ID?” Yes — but it took the first row with that ID, whichever machine it was on. Which machine owns this row?
“Does the project folder path match?” Yes — both copies use the exact same folder path, so the local copy always qualified. Does the machine match too, not just the path?
“Is the project ID the same?” Yes — it is the same project, so the ID is identical on both machines by design. Is there exactly one machine that can claim it?
“Is this project registered?” Yes — the local copy is registered, so the request quietly went local instead of erroring. Is the registered copy the one on this workspace’s machine?
“Is there cached PR data?” Yes — the wrong copy had a perfectly valid cache, so nothing looked broken. Can the answer be proven — or must we refuse and say so?
Root cause in one plain sentence: every lookup answered “does this ID/path exist?” but never “on which machine?”, so with two matching copies the answer was whichever came first in the list.
6 Decision traps
Severity
Myth

“It’s just a stale refresh — clicking Refresh fixes it.”

Reality

It is wrong data and wrong writes. The log you read, the reply you post and the badge you clear can all belong to a different machine. Refreshing doesn’t help — the app is confidently asking the other copy.

Blast radius
Myth

“Everyone is exposed, so this is an emergency.”

Reality

Only setups with the same project on more than one machine — a local clone plus a remote, two paired servers, or a direct SSH connection that a server also proxies. Single-machine users see no change at all. But that multi-machine group is the remote-first audience.

Hold risk
Myth

“Holding is free — the bug is rare and harmless.”

Reality

Holding keeps the wrong-machine writes live: a review reply posted on another PR, a PR badge cleared in a workspace you weren’t looking at, logs that contradict the sidebar. All of it silent, so nobody notices until it matters.

7 Risk analysis & recommendation

Who benefits

  • Anyone who keeps a local clone and a remote/SSH workspace of the same project.
  • Teams on paired servers where two machines expose the same project and folder.
  • Reviewers trusting check logs: the tab and the sidebar finally agree.
  • Anyone who pushes on a remote and expects the PR card to update there.

Who pays

  • Reviewers: 79 files and ~3.2k net lines, 77% of which is tests.
  • Ambiguous setups now see an honest “can’t load” where they previously saw (wrong) data — a visible change for a minority.
  • Check tabs opened on a remote machine no longer reuse the local machine’s tab, so a few users get one extra tab.
  • More routing surface to maintain; the legacy-SSH compatibility path is the part most likely to age.

Recommended
Ship

Hold

Only if you insist on splitting the legacy-SSH tail into its own PR first — that costs another review cycle and leaves the bug live for those rows meanwhile.
