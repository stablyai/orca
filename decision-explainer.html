macOS users see a Settings error and lose the orca terminal command

Decision summary: approve this small, well-bounded fix design — it stops creating unreadable command links, turns a crash-style error into a one-click repair, and changes nothing about which commands Orca is allowed to replace.

✔ Recommendation: SHIP — approve the design

One-line problem

On some Macs, opening Settings shows "permission denied" and the orca command in Terminal is dead — and the app's own Register / Remove buttons fail the same way.

One-line fix

Create future links readable by everyone, recognize an unreadable-but-proven-Ours link as "needs re-registering," and let the existing one-prompt repair flow replace it.

1 Scope boundaries

What a user gets, and what stays untouched.

✅ This change DOES (user-facing protections) 🚫 Does NOT touch (non-regression boundaries)
New installs create a link anyone can read, even on locked-down Macs. Ownership rule — Orca still never replaces a command it cannot prove is its own.
Broken installs show as "needs re-registering" (switch off) instead of an error popup. Unknown links — a link that may belong to another app still refuses repair and shows a manual fix.
One-click repair from Settings, onboarding, and setup panels (single admin prompt). Already-locked folders — system folders the old script already locked down are left alone (message names the path).
Terminal fixed too — repaired link makes orca work again in the shell. Linux / Windows — Linux ignores link permissions; Windows uses a wrapper file. No behavior change there.
Moved-app case stays safe — a link to an Orca app in another location is not auto-replaced. No new privileged code path — repair reuses the existing guarded replacement flow.

4 Why the old check failed

One plain-sentence root cause: the setup script created the link readable only by the administrator, but the status check only expected "link missing," so a "link present but unreadable" crashed through as an error.

Question the old code asked What it concluded (superficial pass) Missing question this change adds
"Is there a link here?" (list folder) Yes — looks registered ✔ —
"Where does the link point?" (read the link text) ✘ Throws "permission denied" — only "link missing" was handled "Can I read the link text?" → if denied by permissions, follow the link through to its destination and compare it with this app.
"Did the link change while I looked?" (retry check) Misreported as "changed while inspecting" after 3 retries "Is this a permissions failure, not a race?" → keep the identity snapshot, skip the retry, classify honestly.
"May I replace it?" (ownership proof) Never reached — the error escaped first "Does the link resolve to this app's own launcher?" → stricter proof than the old path-text match; only then allow the existing guarded replacement.

5 Decision traps — myth vs. reality

Myth — Severity: "just a settings cosmetic"

It looks like a dialog glitch.

The same defect kills the orca Terminal command entirely, and blocks Register / Remove — the user has no in-app way out.

Reality: loud + self-locking — error on every visit, repair buttons fail identically.
Myth — Blast radius: "one user, one mac"

Rare local permissions quirk?

Every macOS admin-prompt registration since v1.4.197 is affected, plus all five status-check surfaces (Settings, onboarding, agent-skill, browser-use, computer-use, orchestration panels).

Reality: systematic for the admin-prompt path — not a one-off.
Myth — Hold risk: "safer to wait"

Holding avoids a privileged-change risk.

There is no new privileged path; the replacement flow and its guards are unchanged. Waiting leaves affected users with a dead command and a dead-end error, plus a manual sudo chmod workaround as the only exit.

Reality: holding is the risky option — the harm is happening now, the fix reuses proven flows.

6 Risk analysis & final recommendation

Who benefits

Affected Mac users regain Settings + Terminal with one familiar admin prompt; support gets a displayable status ("needs re-registering" / conflict with fix line) instead of an error string; future installs stop creating the defect, including on managed Macs.

Who pays

Users with a genuinely foreign unreadable link see a conflict and a one-line manual command; users whose Orca app moved location are not auto-repaired (documented, rare); auto-register flows (onboarding, setup panels) will surface the legitimate repair prompt once.

✅ SHIP — approve the design (recommended)

Tiny, bounded, reuses existing guarded flows; refusal guarantee intact; tests enumerated for all four link shapes.

⏸ HOLD — only if…

…you also want the locked-folder (lstat-denied) case mapped to a displayable status — ask for that as a named follow-up, not a blocker.

🧰 WRONG TOOL — if…

…you expected a hotfix for already-locked system folders or silent auto-repair of moved-app links — those are explicitly out of scope by design.
