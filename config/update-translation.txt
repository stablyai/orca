# Translation scan tracker

Recurring task: after a batch of merged PRs, scan for i18n gaps and fix them:
1. unkeyed user-visible UI strings (gate: `audit:localization` / `verify:localization-coverage`),
2. keyed strings missing target-locale translations (en.json has the key, es/fr/ja/ko/zh does not),
3. badly translated target values (placeholder mismatch, brand/term policy violations).

Method (reproducible):
- `node config/scripts/verify-localization-catalog.mjs` — key references vs en.json,
  per-locale coverage, interpolation mismatches, generic-term regressions.
- `node config/scripts/audit-localization-coverage.mjs --check` — unkeyed strings.
- `node config/scripts/verify-localization-extraction.mjs` — en.json in sync with code.
- Missing-key delta since last scan: flatten en.json at HEAD vs at the last-scanned
  base commit, keep keys absent from each target locale.
- Translate the delta per `config/i18n-translation-source.md` policy and the overrides in
  `config/scripts/locale-*-overrides.mjs` / `locale-*-fixes.mjs` / `locale-generic-ui-terms.mjs`
  (brands such as Orca/OpenCode/Git/Python stay Latin; `{{placeholders}}`, markdown links,
  backtick code spans, and `[python.org](...)` links are preserved verbatim).
- Apply with `node config/scripts/apply-translation-delta.mjs /tmp/translations.json`
  (validates placeholder parity and runs every value through `repairTranslatedValue`
  so CJK spacing, brand-mistranslation fixes, and phrase fixes match the repo pipeline).
- Re-run all four gates plus the vitest locale suites before finishing.
- Mobile (`mobile/`) has no locale catalogs (only SVG `translate()` transforms); out of scope
  until the mobile catalog migration lands. Missing keys fall back to English at runtime
  (sparse-catalog architecture, PR #8512), so untranslated leftovers are safe, not broken.
