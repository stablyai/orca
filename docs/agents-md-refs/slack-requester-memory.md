# Slack requester memory implementation status

The public host accepts an optional `asker.slackRequester` stamp on connector starts and sends. It carries a Slack installation workspace ID and the direct human author's Slack user ID. The host checks that the user ID agrees with the asker, excludes apps and delegated bot posts, and checks the workspace against the receiving bot's configured Slack apps before writing the stamp to the journal. An old or ambiguous delivery still reaches the bot without the stamp. Every message carried into a stamped batch must name the same verified requester.

## Implemented in the public host

- The internal launcher reserves an immutable host database binding through the bots database worker before creating a native session. The binding records the bot, workspace, requester, original Slack destination, reply account, delivery ID, and operation ID. A launch or restart requires that binding and a native local Codex record in its workspace. The provider uses a dedicated working directory, the reply-only policy, and scoped instructions. Orca skips the normal bot preamble, linked skills, visuals, and bot tool servers.
- Native send admission requires both the original operation and an in-process connector capability. Owner text, mail, creation messages, fork or adoption into the scope, prompt responses, thread goals, and conversation commands cannot enter through their ordinary admission paths. Each admitted delivery retains its original Slack destination in the durable reply outbox. Only dormant isolated links qualify to be replaced after the host checks their open work and unfilled replies. Existing legacy links stay on their previous chat.
- Codex's scoped memory tool handles read, remember, and forget. It accepts calls from the active turn on the acquired provider thread and takes its scope from the launch binding. Its arguments accept no bot, workspace, requester, or path. An ambiguous requester gets no memory text and no memory tool. Index and topic writes are serialized per file and use owner-only durable writes.
- The isolated link disables Slack prompt publication, Slack prompt answers, mirroring, and the legacy reply-text path. Production still uses the ordinary launcher. The scoped launcher has no production selector or user setting.

## Local provider validation

An isolated smoke run used the installed Codex App Server 0.170.0 on macOS arm64. It composed the public host's launch, sent four synthetic turns through a loopback Responses fixture, handled the provider's native tool calls, and filled a fake Slack outbox with the resulting replies. The App Server ran with a temporary home, temporary Codex configuration, and loopback-only outbound networking.

- Two requesters in the same synthetic Slack thread had distinct provider threads and distinct facts. The native tool read, remembered, and forgot a fact, and refused a call that supplied another requester ID. Reopening the host database and starting a new App Server resumed the original provider thread and returned the updated facts.
- The App Server reported `readOnly` with `networkAccess: false`. Host overrides disabled a fixture MCP server and removed goal tools from the model's tool list. Codex still advertised `request_user_input` and refused the actual call in Default mode. The ambiguous requester received neither memory data nor the memory tool. None of the model requests contained the ordinary bot preamble sentinel.
- Every synthetic reply filled only the expected delivery row for the original Slack thread. This exercised the local protocol and reply fill with synthetic inputs. Hosted delivery, Slack posting, authenticated model inference, and other Codex versions were outside the smoke run.

## Current routing

- The hosted connector accepts Slack events and produces authenticated Orca Cloud deliveries. The public repository contains its wire contract, while the [connector service runs outside this repository](../../cloud/README.md). The current public contract identifies an authorized asker, a channel, and an optional message action reference. It also permits a Slack app or a bot posting for a person. An install's bot user, installer, or owner record does not identify a specific event's human author.
- `dispatchDelivery` forwards the connector's structured asker to the external-conversation seam. `botChatFor` normally reuses one linked native chat per Slack thread, and some older DM routes use the bot's Home Chat. `deliverToChat` admits requests with `delivery: 'now'`, which can steer another request into an active turn. The journal records the opener and can also have other messages inside that turn. The older cloud reply path and the outbox reply path use the same chat admission. The difference is how the reply gets to Slack.
- Bot session launch reads `SOUL.md` and the bot home's shared `MEMORY.md` into its instructions. Several providers resume with the original instructions and prior messages. The turn context also tracks what index and topic changes the session has seen. The topic files in `memory/` are available by direct filesystem reads, and the host tracks their changes for memory receipts.
- An agent can edit the shared index and topic files directly. Turn-end reconciliation restores missing index facts and records changes through a per-bot queue. `orca bot memory forget --fact` calls `bots.memory.forget`, which also operates on the shared index and its record. Direct topic edits do not use that index operation. The history file, undo, tidy-up, and work journal all use the existing shared scope.
- The available bot settings include Slack connections and access, Slack mirroring, launch options, and shared memory and tidy-up. The existing bot commands and provider preamble still use shared memory on the ordinary launcher.

## Before enabling requester memory for a running bot

1. Update the hosted producer to stamp only a verified human Slack event, using the workspace of the receiving installation and the event author's ID. Exercise DMs, mentions, replies, Slack Connect routing, apps, posts made by another Orca bot, and queued deliveries from older builds. Leave the stamp absent when the producer cannot establish both IDs.
2. Pin a supported Codex App Server build. The local 0.170.0 run verified native tool registration, invocation, resume, and reply-only policy. Qualify the pinned build with the release configurations and authenticated provider in a test environment before enabling it for a bot.
3. Validate handoff and reply recovery across restart with the hosted outbox, including late replies, usage-limit cuts, and aborted turns. Older legacy turn ends have no durable per-delivery route. Existing legacy threads require a drained cutover or a new Slack thread. When opening a fresh provider context, obtain Slack thread history from the source, since follow-up deliveries may include incremental history only.
4. Verify two requesters in separate threads and in one thread, including concurrent requests, prompt handling, restart, and forget. Then expose a per-bot setting, default it to off, and opt in the intended bot. Pause Slack admission before rollback. Keep a compatible host available for journals written with the new stamp and keep scoped provider contexts isolated from ordinary sessions.

Slack thread replies remain visible to the thread's participants. The host's reply-only policy limits provider tools. Earlier Slack posts and provider transcripts have their own retention.
