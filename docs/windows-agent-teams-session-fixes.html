Claude Agent Teams on Windows — every bug found and fixed

2026-07-27 → 07-28Orca 1.4.148-rc.1Claude Code 2.1.22016 defects

Agent Teams didn't work on Windows because of three deliberate platform guards. Once those came out, sixteen more defects surfaced.

Fifteen were POSIX assumptions in code that had never been executed on Windows — not poorly written, unexercised. The sixteenth was a deployment cache that quietly stopped the fifteenth fix from ever reaching the running process, and cost the most time of any of them.

Why it happened

Root cause class 1 — unexercised platform (defects 1–15). Every assumption that is true on POSIX and false on Windows survived untested:

POSIX assumptionWindows reality
process.env.PATH existsnative processes expose Path
a spawn finds any executable on PATHCreateProcess appends .exe, never .cmd
copyFile doesn't preserve mtimeon Windows it does
stdin is a TTY if stdout isElectron-as-node breaks that pairing
env keys are case-sensitivecase-insensitive, so duplicates collide
the pane's shell understands && and env K=VPowerShell understands neither
cat holds a pane openalias for Get-Content, which prompts
a quoted path is a commandin PowerShell it's a string expression

Root cause class 2 — a cache keyed on the wrong thing (defect 16). Not a Windows bug at all. Orca's PTY daemon refreshes only when the app version string changes. Every local rebuild carries the same version, so the daemon ran day-old code through every reinstall.

The starting misdiagnosis is worth recording. The theory was "Orca needs tmux, Windows has none, so install psmux." Orca never runs tmux on any platform — it impersonates one: tmux -V returns the hardcoded string tmux 3.4. So psmux could never have helped, and it proved an active hazard: its real tmux.exe wins a bare-name lookup a .cmd shim can't compete in.

The original blocker

Removing them was correct. It was also roughly a fifth of the work.

Group A — platform assumptions

15

A quoted executable path is not a command

user-reportedunverified
Symptom
At line:100 char:43
+ 'C:\Users\ECQ944\.local\bin\claude.exe' --agent-id arch-reviewer@sess ...
Unexpected token 'agent-id' in expression or statement.
The '--' operator works only on variables or on properties.
How

Once 13/14 removed the POSIX wrapper, the pane's command became a bare 'C:\…\claude.exe' --agent-id …. On Windows that text is appended to an OSC 133 bootstrap and delivered via -EncodedCommand, so it is evaluated as PowerShell source. PowerShell reads a leading quoted token as a string literal, then chokes on --. The line:100 is the tell — the bootstrap is ~99 lines.

Why

Orca's own callers hand-write invocable commands (& 'codex' …). Agent-teams structurally cannot: it relays text Claude composed for a POSIX shell.

Fix

ensurePowerShellInvocable prefixes & when a command begins with a quoted token, applied where the command becomes PowerShell source — the only layer that knows the pane's shell. Guarded so & 'x', . profile.ps1 and bare claude … are untouched.

13

Claude's teammate command is POSIX shell

user-reportedfix unobserved
Symptom
+ cd 'C:\...\kaizen-designer-agent' && env CLAUDECODE=1 CL ...
The token '&&' is not a valid statement separator in this version.
How

Claude hands the shim a POSIX shell string and the dispatcher passed it straight to splitTerminal as the pane's command. PowerShell 5.1 has no &&, and env K=V cmd isn't a command there.

Why

On POSIX panes the shell interprets it correctly. A pre-existing test encoded the exact string and asserted it was forwarded verbatim — right on POSIX, wrong everywhere else.

Fix

Decompose instead of translating, so no shell syntax is emitted at all: cd becomes a cwd option, env K=V merges into the existing env option, and the remainder is a bare command. That runs identically under PowerShell, cmd and Git Bash. cwd was threaded through the split so a teammate in another worktree starts in the right place — silently running an agent in the wrong repository is damaging, not cosmetic.

Why not translate: I offered translation as the cheap option and withdrew it. The dispatcher cannot see the pane's shell at all — it's resolved in the daemon PTY layer — so translating is more plumbing than adding cwd, and there's no common syntax to target (set K=V vs $env:K='V', && vs ;).

14

The holding pane ran cat

user-reportedfix unobserved
Symptom
cmdlet Get-Content at command pipeline position 1
Supply values for the following parameters:
Path[0]:
How

Claude splits a placeholder pane running cat, then respawns it with the real command. On POSIX cat reads stdin and holds the pane quietly. In PowerShell it's an alias for Get-Content, which blocks prompting for a path.

Fix

On Windows the placeholder starts as a plain shell with no command. It holds the pane just as well and is replaced moments later anyway.

11

spawn claude ENOENT

user-reportedverified fixed
How

The teammate PATH was [shimDir, args.baseEnv.PATH].filter(Boolean).join(';'). A native Windows caller sends Path, so baseEnv.PATH was undefined, filter(Boolean) dropped it, and PATH became one directory.

Why

POSIX shells and Git Bash both expose PATH, so every test and developer run saw the uppercase key.

Fix

New env-var-casing.ts. Reads either casing, and writes back under the caller's own key — emitting PATH when the child already has Path leaves two keys with undefined precedence.

before:  caller sends Path  ->  PATH had  1 entry  -> ENOENT
after :  caller sends Path  ->  Path had 60 entries -> resolves
12

Claude launched but rendered nothing

user-reportedfix inferred
How

The Windows launch command was orca.cmd claude-teams, running the CLI inside Electron-as-node, which spawns Claude with stdio: 'inherit'. Measured in the same pane:

node              stdout.isTTY: true   stdin.isTTY: true
electron-as-node  stdout.isTTY: true   stdin.isTTY: FALSE

Claude is an interactive TUI; with non-TTY stdin it can't enter raw-mode input. The process ran 20+ minutes silently.

Fix

Windows launch command → claude --teammate-mode auto, launched directly by the PTY with a real TTY.

5

Batch shim targets couldn't be launched

verified fixed
How

UseShellExecute = false with a default target of orca.cmd. CreateProcess cannot execute a batch file, so any .cmd target — including the whole dev path — threw at startup.

Fix

Batch targets route through cmd.exe /s /c with each argument quoted.

7

Shim copy re-ran every launch, and would have gone red in CI

verified fixed
How

copyIfChanged compared size and mtime, but copyFile preserves mtime on Windows and not on POSIX. The test passed locally and would have failed on the Linux CI that runs the suite.

Fix

Stamp the target with utimes after copying.

8

node:sqlite blocked packaging entirely

verified fixed
How

The packaged-runtime verifier built its allowlist from builtinModules, which omits prefix-only builtins (node:sqlite, node:test, node:sea) on every Node version. The main bundle legitimately requires node:sqlite, so afterPack aborted.

Fix

Also accept isBuiltin(specifier). This one exists upstream — the file is byte-identical on origin/main, and no Node upgrade fixes it. Worth submitting separately.

9

send-keys typed key names as text

verified fixed
How

Only 15 keys were mapped. Arrows, Home, End, PPage/NPage, IC/DC, BTab and most chords fell through as literal text — send-keys Left typed "Left". I hit this directly: my keystroke landed as text in Claude's prompt.

Fix

Named-key table plus a general chord rule using charCode & 0x1f. The intuitive - 96 is wrong for C-[ — negative code point. F1–F12 deferred.

Group B — test defects

Worth dwelling on, because the suite was green while the feature was completely broken.

4

The load-bearing acceptance test was vacuous

verified fixed
How

The entire justification for shipping a compiled .exe was "Orca must win the tmux lookup against a competing port." The test asserted only negatives:

expect(result.stderr).not.toContain('DECOY_WINS')
expect(result.status).not.toBe(99)

…with the shim target set to echo, which isn't an executable. The shim errored and both assertions passed on the failure path. It would have passed for an empty program.

Fix

Assert a positive — a recording stub must receive ['agent-teams-tmux', '-V'].

3

The integration tests compiled the wrong binary

verified fixed
How

buildStubExe wrote a stub then built with --target orca, which compiles OrcaCliLauncher.cs. The stub was never used. The file's header blamed "needs a full Orca installation" — a misdiagnosis of its own bug, written into a comment.

Fix

Added --source <path> to the build script.

2

The shim fabricated a version string to satisfy a test

verified fixed
How

OrcaTmuxShim.cs wrote tmux 3.4 to stderr unconditionally on every invocation, commented "version sentinel consumed by the build-script integration test." Production behaviour altered to make a test pass — and a sentinel test would have passed with forwarding entirely broken.

Fix

Removed. A build test now asserts the binary doesn't embed it, replacing one that asserted the opposite.

Group C — incomplete gating

10

A fourth win32 gate

user-reportedverified fixed
How

tui-agent-config.ts carried detectUnsupportedRuntimes: ['win32','wsl'] — a different mechanism from the three original gates. Those control the launch plan; this controls whether the agent is detected at all, so Settings showed "Available to install" regardless.

Why

I grepped the renderer for claudeAgentTeamsMode, got no hits, and reported "there is no settings UI on any platform." The UI is keyed on the agent id claude-agent-teams. Wrong search string, then a negative stated more confidently than the search supported.

Fix

['wsl']. WSL stays unsupported deliberately — the shim calls back into the host Orca process.

Group D — implementation slips

1

The shim never reached the dispatcher

verified fixed
How
FileName  = shimBin

Arguments must exclude the program. The child got argv[0] = <path> while the CLI dispatches on argv[0]. Every forwarded tmux call failed silently.

Copied from OrcaCliLauncher, where including cliPath is correct because there it genuinely is Electron's first argument.

Group E — deployment

The one that isn't a Windows bug, and the one that cost the most time.

16

The daemon never refreshes across same-version builds

not fixed
Symptom

Fix 15 was correct, present in out/, in the installer, and in the installed app.asar — and had no effect across three reinstall cycles.

How

Orca runs PTYs in a separate long-lived daemon, materialised into a directory keyed only on the app version:

%LOCALAPPDATA%\Orca\daemon-host\1.4.148-rc.1\
  .materialized.json  {"version":"1.4.148-rc.1","completedAt":"2026-07-27T09:38:46.922Z", …}

const existing = getRelocatedDaemonHost()   // version matches, files exist
if (existing) return existing               // -> never re-copies

No content check. Every build in this effort was stamped 1.4.148-rc.1, so the daemon host stayed frozen at the 27 July copy:

chunkbuilthas fix 15
daemon (in use)…-BrBGSYKg.js27/07 17:38false
installed app…-Dd33jS70.js28/07 10:20true

The daemon process (PID 22292, started 27/07 21:51:50) survived every reinstall.

Why

Every obvious remedy fails, and fails silently:

  • Reinstalling doesn't touch the daemon host — the marker still matches.
  • Deleting the directory fails while the daemon holds the .exe; the publish step is rmSync(dest) then renameSync, and the failure is caught and fail-opened.
  • Killing the daemon alone doesn't help: on next launch the marker still matches, so materialisation short-circuits before doing any work.

This masked only daemon-executed code — which matches the history exactly. Defects 10, 11, 12 and 13/14 live in the main process and took effect on reinstall; 15 lives in the daemon and did not.

Fix

The marker was removed by hand locally; the daemon still needs stopping so the re-copy can publish. No code change made. The proper fix is keying materialisation on a content hash of the daemon sources — but that changes how every Orca installation decides to refresh, too broad to land as a side effect of a Windows bug hunt.

Arguably the more valuable fix is making a failed refresh observable: today "couldn't update" is indistinguishable from "already current", so the symptom surfaces far away as a daemon running old code while every artifact check passes.

The question open all session — now answered

For most of this session I could not make Claude spawn a teammate. It exposes no creation tool to the model and no slash command, and every prompt produced a subagent, a different feature. I recorded that the trigger might be unreachable and the whole effort possibly moot.

It isn't. Defects 13 and 14 are Claude's own teammate commands failing inside panes the shim had already created. split-window was reached, the pane existed, the shim round-tripped. Claude invokes it correctly; only the command content was wrong.

The error was specific and instructive: repeated failure to trigger the feature through instrumentation was treated as evidence about the feature, when it was evidence about the instrumentation.

Verified

Confirmed against the running, installed build — checking the install, not the build output:

  • installed app.asar contains every shipped fix, including the cwd override
  • tmux.exe deployed to the user shim dir with matching size and mtime
  • caller sending Path yields a 60-entry PATH with claude.exe resolvable
  • preflight.detectAgents returns claude-agent-teams
  • orca claude-teams spawns claude --teammate-mode auto — no ENOENT
  • the dispatcher drives real panes: split-window, send-keys, capture-pane, kill-pane, respawn-pane
  • Claude invokes the shim and creates teammate panes

Not confirmed

Defect 15 working. Implemented, unit-tested, present in the installed app — but never observed running, because defect 16 blocked its deployment for the entire session.

A teammate pane rendering and working. The outcome all of this exists for.

A teammate launch on macOS or Linux. Decomposition now applies there too, where the string previously ran as shell syntax.

Deliberately not fixed

  • The same PATH-casing pattern in terminal-attribution.ts and pty.ts:971/979. Notably pty.ts:533 already reads both casings — someone hit this before and fixed it narrowly. The attribution one affects every Orca terminal on Windows.
  • F1–F12 in send-keys.
  • Process labelling — launching Claude directly makes recognition register plain "Claude". Believed cosmetic; unverified.
  • Parser coverage is bounded by observation. Only shapes Claude has been seen to emit are recognised; a pipeline or second && would fall through to passthrough and fail as before.

Process notes worth keeping

Five of these were found by the user, not by me — 10, 11, 12, 13/14 and 15 — each after I had reported the flow verified. Several had already appeared in my own session output and been read past: a probe returning a shim-dir-only PATH, and a pane producing no output that I dismissed as a test-harness artifact.

Three of my verification methods passed while the system stayed broken, and each produced confidence that delayed the real diagnosis:

  • Grepping the 115 MB asar container for a symbol → reported a present fix as "MISSING". Extraction is the correct method; a hit is trustworthy, a miss is not.
  • Grepping daemon-entry.js alone → concluded the daemon lacked the fix, when the code lived in a chunk that entry imports.
  • Verifying the installer, then the installed app, then declaring it fixed → never checking what the live process was executing. That is what cost three cycles.

The generalisable rule: proving a component correct in isolation is not evidence that the user-facing path works. Verification has to reach the running process.

I was also wrong three times on diagnosis before measurement corrected me — assuming node-gyp didn't support VS 2026 (it did; the install had no C++ compiler), that Node 24 would fix the node:sqlite check (24.18 omits sqlite too), and that shell translation needed no API changes (it needs the pane's shell, which the dispatcher cannot see).

And once while fixing 13/14 I nearly reproduced defect 7 — reading process.platform inside the dispatcher, so the test would pass on Windows and fail on Linux CI. It's now a pure parameterised function with both branches asserted.

Build obstacles — not code defects

  • No MSVC toolset. VS Build Tools 2026 installed without the C++ workload. Worked around by reusing the ABI-148 windows-native-registry binary from the installed app (Electron 43 → Node 24.18 → ABI 148, exact match). It lives in node_modules and dies on the next pnpm install.
  • Packaging forces a native rebuild. The beforeBuild hook hardcodes --force. Temporarily removed per package, reverted after each one.
  • Disk exhaustion. Two builds died on ENOSPC; one truncated a finished 165 MB installer to 64 MB. A package needs ~1 GB of working space; the machine was at 210 MB.
  • max-lines hit, not suppressed. The dispatcher reached 308 against a 300 limit. AGENTS.md forbids a disable, so the launch resolver was extracted into its own module — 295 lines, ratchet clean.
