# Use a shared Scryer Read Surface

`readView(...)` must become a real read facade for model overview, subtree, search, query, rules, and codebase reads instead of remaining a thin alias for `scryer.model.read`. The read/query migration needs shared structured result types so UI, CLI, agents, and future adapters do not each reinterpret `model`, `view: unknown`, search hits, query hits, and subtree data differently. The Native Scryer Engine owns read payload generation through a shared read selector; CLI, IPC, UI, and agents consume those payloads instead of generating their own read views from raw model files. The `scryer.model.read` result from the foundation PR is provisional; #16 should replace it with the formal read-surface input/result model and update current callers in the same slice rather than carrying compatibility fields forward.

Upstream Scryer sets the strategy: a read without a node returns overview, a node-scoped read returns a detailed subtree, oversized subtrees degrade to a child skeleton, and agents use search/query to locate a node before reading details. Orca keeps full-model reads available for explicit export, backup, debug, golden fixture, legacy compatibility, cross-subtree restructuring, and direct user-request cases, but full must not be the default or an implicit fallback. Orca will not require a schema-level purpose field for full reads; agents and adapters choose full when their task needs it, guided by the read mode policy. The overview payload therefore has to carry enough navigation signal for agents to choose the next read: ids, breadcrumbs, counts, hidden-symbol indicators, source/boundary/link coverage, and recommended follow-up reads.
