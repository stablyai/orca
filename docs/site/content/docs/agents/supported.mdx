Orca works with **any CLI agent** — the agent combobox just launches a process in a terminal. The following ship preconfigured in the built-in agent picker with one-click launch/setup; deeper hooks, status, usage tracking, and account switching are noted where supported.

<Callout title="Permission safety">
  The defaults below pass each agent's permission-bypass flag for new launches. A worktree is an
  isolated checkout, not a security sandbox: the agent can still access files and network resources
  available to its process. Choose **Manual** in **Settings → Agents → Agent Permissions** unless
  you intentionally trust the agent and the task.
</Callout>

## Permissions default

For new launches, Orca pre-fills each supported CLI's permission-bypass flag — `--dangerously-skip-permissions` for Claude, `--dangerously-bypass-approvals-and-sandbox` for Codex, `--yolo` for Gemini / Cursor / Crush / Kimi / Muse / Rovo Dev / Hermes / GitHub Copilot / Command Code, `--mode yolo` for ZCode, plus the equivalent flag for every other agent that exposes one. These flags allow an agent to act without confirming every shell command; review the trust boundary before using them.

Use **Settings → Agents → Agent Permissions** when you want to switch all uncustomized agents between **Yolo** and **Manual** launches. If you already overrode a specific agent's launch arguments or environment, Orca leaves that agent alone so the global switch doesn't erase your custom command.

To restore prompts for one agent only, edit that agent's default arguments or environment in Settings. Orca treats a non-empty custom value as an explicit override and opts that agent out of future permission-mode migrations.

## OMP: live subagent status

Orca's managed status extension observes OMP's own agent registry. Children appear by their native
IDs rather than repeated role names, and completed or cancelled children leave the live roster.
Registry changes are coalesced for about 200 ms; active work is rechecked every five seconds, including
when the parent is silently waiting. These checks verify running agents, not new model activity.
Children waiting for background tool results remain live even when OMP temporarily marks their
model loop idle. Opening an unprompted OMP session does not count as working.

After upgrading Orca, fully restart the app and OMP to load the updated tracking code and extension.
No additional tracking tool, daemon, or model instruction is needed. Native tracking is
capability-detected and has been verified with OMP 18.10.3, 18.10.4, and 18.11.0; runtimes without the
registry API retain lifecycle-only tracking. Agent roles do not restrict which children are tracked.

Snapshots belong to one root and its current session. Session changes retire the previous roster,
and observation refreshes preserve the root's prompt, input waits, and turn timing. Failed registry
reads or hook delivery cannot refresh stale child evidence or declare an agent exited.
Queued turn completions can still retry after shutdown releases the pane; these final messages
do not replay child rosters.

The existing compact sidebar layout is unchanged. Expand the worktree's agent count, then use the
chevron on an OMP parent row to show or hide its children; there is no separate subagent switch.
When OMP reports a new session ID and transcript, the renderer cannot inherit the previous session's
turn clock. The root's own completion time remains separate from its children's.

OMP paints shell-completion markers inside its prompt bubbles while the process is still running.
Orca checks that the foreground has returned to a shell before retiring that OMP launch; an
unverifiable foreground read does not close its status channel.
If the controller is temporarily absent, Orca retries when it reattaches, using the original launch
and title identity. Newer completion markers supersede pending checks, and PTY exit discards them.
Overlapping checks publish only the newest completion marker and exit code, including reattached
OMP terminals without a launch token.

Delivery keeps current and adjacent closing scopes rather than replaying an unbounded history after
an outage. Older retired updates may be discarded; the status feed is not a durable notification log.

For SSH workspaces, the execution host owns the registry and hook store; use an updated Orca host and
a compatible OMP there. Losing client contact remains `unverifiable`, not `exited`. The adapter does
not require a git worktree, so the same observation works in folder workspaces.

The shared roster displays up to 32 children. Root completion accounts for all discovered native
children, including those beyond that display limit.

The optional installed-OMP E2E uses one core scenario: two sessions with three children by default.
`ORCA_OMP_SCALE=1` adds eight sessions with six children; `ORCA_OMP_SCALE_STRESS=1` adds sixteen with eight.
It checks live rosters, quiet/background work, cancellation/completion and session isolation, with a
smoke check of the existing compact UI rather than repeating its disclosure or accessibility tests.
Run `ORCA_BACKGROUND_LAUNCH=1 ORCA_REAL_OMP_CLI_TEST=1 pnpm run test:e2e omp-subagent-status.spec.ts --workers=1`.
The core suite was verified with OMP 18.10.4; it is a functional check, not a benchmark harness.

## ZCode: pick a CLI that ships the TUI

Orca drives ZCode through the `zcode` terminal CLI, so `zcode` on your `PATH` has to be a build that
includes ZCode's TUI.

The ZCode **desktop app** bundles the agent runtime without it. Pointing `zcode` at
`/Applications/ZCode.app/Contents/Resources/glm/zcode.cjs` starts, then fails to open a session with:

```
Cannot find package '@zcode/tui' imported from .../zcode.cjs
```

Orca's hooks still install correctly in that state, so the symptom looks like a broken integration when
it is really a CLI that cannot render a session. Use a `zcode` that carries the TUI — build the CLI from
[`zai-org/ZCode`](https://github.com/zai-org/ZCode) (`apps/zcode-cli`), or install a distribution that
packages the runtime together with the TUI.

Check what you have with `zcode --version`, and confirm `zcode` opens a session outside Orca before
reporting a harness problem.
