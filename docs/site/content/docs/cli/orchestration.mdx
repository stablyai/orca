Orchestration is Orca's structured multi-agent layer: a **Run** (namespace + coordinator inbox), **Tasks**, **Dispatches**, supervised **workers**, messages, and decision gates.

Use it when you need ownership, completion tracking, or a DAG. To send another agent a one-way message, use `orca orchestration send --to <terminal handle or orca_session_id:<id>> --subject "<topic>" --body "<message>"`; it needs no Run or Task. For full ownership handoffs without supervision, use `worktree create --agent` or `agent launch` from the `orca-cli` skill.

<Callout title="Experimental">
  Enable orchestration under Settings → Experimental before using these commands. The CLI talks to
  the running Orca runtime, so `orca status --json` should succeed first.
</Callout>

<Callout title="Legacy commands retired">
  `orca orchestration run` and `run-stop` (and `coordinator-start` / `coordinator-stop`) perform
  **no effects**. They return recovery text pointing at `orca skills get orchestration --full`. Use
  the Run + worker-start flow below.
</Callout>

## Output

Every orchestration command prints a short view by default: the IDs and state the next command needs, with the next step last. `--json` prints the same fields as one line of JSON (`{"ok":true,"result":{...}}`). `--full --json` prints the complete record Orca returned as pretty JSON; `--full` alone prints the longer text receipt. A failed or unconfirmed outcome exits non-zero and writes `error: <code>: <message>` to stderr.

## Core model

- **Run** — durable namespace and home inbox. Never schedules or places workers.
- **Task** — a work item with a spec, dependencies, and status: `pending`, `ready`, `dispatched`, `completed`, `failed`, or `blocked`.
- **Dispatch** — one attempt of a task on a terminal; lifecycle authority for `worker_done`.
- **Message** — inbox mail (`status`, `dispatch`, `worker_done`, `escalation`, `question`, `heartbeat`, …).
- **Decision gate** — a coordinator-owned question that blocks a task until it is resolved.

Completion authority comes from the active dispatch context. Worker completion messages should include both `taskId` and `dispatchId`.

Task IDs printed in terminals, such as `task_...`, are clickable links. Clicking one asks the Orca runtime for the task's current dispatch and focuses the assigned terminal, including when the task lives in a remote or SSH runtime.

## Preferred supervised loop

```bash
orca orchestration run-create --objective "Split checkout QA and summarize blockers"
orca orchestration task-create --spec "Audit billing settings for mobile layout" --task-title "Billing audit"
orca orchestration worker-start --task <taskId> --worktree current --agent codex
# or new worktree:
orca orchestration worker-start --task <taskId> --worktree new-child --name billing-audit --agent codex --setup run
# optional per-worker model / effort (Claude, Codex, Cursor, Antigravity, Grok, Muse, Pi; not with --terminal):
orca orchestration worker-start --task <taskId> --worktree current --agent claude --model <opaque-model-id> --effort high
```

`--agent` takes any Orca agent ID enabled on the worker server, for example `claude`, `codex`, `cursor`, `antigravity`, `muse`, `opencode`, or `opencode2`. `--model` accepts opaque provider model IDs for Claude, Codex, Cursor, Antigravity, Grok, Muse, and Pi (for example `--agent muse --model muse-spark-1.3`); Pi takes a `provider/id` selector and maps `--effort` to its own `--thinking` level (off, minimal, low, medium, high, xhigh, max); OpenCode accepts a per-launch model only in an existing worktree, when the execution host verifies its CLI version and model availability; OpenCode effort remains unsupported. Other agents run the model from their own config. `--effort` requires `--model` and only applies when that agent/model supports the level. Neither flag can combine with `--terminal` (reuse an existing pane). Overrides apply to that launch only and show as `model` / `effort` in the start receipt (`--full --json` shows `launch.requested` / `launch.effective`). Federated starts need a worker host that advertises launch-preference support.

After starting workers, end your turn. Orca wakes the coordinator when a worker reports, asks, or stops. In a chat, each message arrives whole: act on it. When the wake names a `check` command (a terminal, or a chat message too large to deliver whole), run it and handle every message it prints:

```bash
orca orchestration check --run <runId>
```

Worker completion (from the worker pane; include injected IDs):

```bash
orca orchestration send \
  --type worker_done \
  --subject "Completed mobile audit" \
  --body "Fixed footer overlap; no follow-ups." \
  --task-id <taskId> \
  --dispatch-id <dispatchId> \
  --outcome succeeded \
  --files-modified "src/app/settings/Billing.tsx"
```

`worker_done` requires `--outcome succeeded|failed`.

Inspect / recover:

```bash
orca orchestration worker-show --dispatch <dispatchId>
orca orchestration worker-read --dispatch <dispatchId> --limit 50
orca orchestration worker-stop --dispatch <dispatchId>
# After an accepted worker_done: reuse the same terminal for a follow-up Dispatch, or release it
# (archives inspectable output, then closes only that coordinator-owned agent terminal):
orca orchestration worker-release --dispatch <dispatchId>
# Keep a worker open after it finishes (or start it with worker-start --keep-open):
orca orchestration worker-keep-open --dispatch <dispatchId>
# retry placement is explicit — --retry-of does not inherit --on/worktree:
orca orchestration worker-start --task <taskId> --retry-of <dispatchId> --worktree current --agent codex
```

When a worker stops at a permission prompt, the escalation names the prompt. Only a person can allow it, so carry on with other work until its closing message arrives; if it is holding up the task, deny it with a reason and the worker carries on another way:

```bash
orca orchestration deny --dispatch <dispatchId> --prompt <approvalId> --reason "<what to do instead>"
```

If the user turns on **Let coordinators approve worker permission prompts** in Orca's orchestration settings, the coordinator may also allow it with a reason. The user still sees Allow and Deny, and the first answer wins. The machine running the worker applies its own setting:

```bash
orca orchestration approve --dispatch <dispatchId> --prompt <approvalId> --reason "<reason>"
```

Do not leave completed worker terminals open just to re-read output — use `worker-read` after `worker-release`. Do not substitute a broad `terminal close` when release returns `release_pending` or `release_unknown`; follow the receipt's recovery action.

## Federated workers (optional)

For a new worktree in another project or on a named machine, run `orca host list --json` (only `kind: environment` rows are paired servers; ask if a user-supplied name matches multiple host kinds, such as an SSH target and a server) and compare `orca project setups --environment local --json` with `orca project setups --environment <server-id> --json` for each paired server. Match by `projectId` and select a row on the answering machine with `setupState: ready`, a non-empty `repoId`, `kind` other than `folder`, and `hostId: local`. Pass its `repoId` as `--repo id:<repoId>`. A row whose `hostId` is not `local` describes an SSH target behind the server and cannot host a new worktree via `--on`: if that is the only setup, or a pinned machine has no usable setup, do not start it — tell the user where it is registered and why it cannot be used. Work in an existing workspace uses its exact worktree selector without `--repo`.

Honor the user's machine choice. For the full selection order and how to record placement in the Task spec, run `orca skills get orchestration --reference references/placement-and-remote.md`.

```bash
orca orchestration worker-start \
  --task <taskId> \
  --on windows \
  --worktree new-top-level \
  --repo id:<repoId> \
  --name remote-worker \
  --agent codex \
  --setup run
orca orchestration send --to dispatch:<dispatchId> --subject "Follow-up" --body "…"
```

Use `--worktree new-child` instead to nest the server's worktree under your workspace in the sidebar. A server too old to nest across machines still starts the worker, top-level, with a `warning` in the receipt.

Later commands route by Dispatch ID; do not repeat `--on`.

## Low-level dispatch (custom topology)

```bash
orca worktree create --name billing-audit --agent codex --json
orca terminal wait --terminal <workerHandle> --for tui-idle --timeout-ms 60000 --json
orca orchestration dispatch --task <taskId> --to <workerHandle> --inject
```

## Messaging notes

- Default `check` returns the bound Run's oldest unread mail as one Delivery (FIFO) and marks it handled. `--ack <deliveryId>` acknowledges a Delivery from an older Orca that does not mark it; alone it reads no new mail, and with `--wait` it then waits for and takes the next Delivery.
- `--peek` / `--all` do not consume mail and return no `deliveryId`, so they do not drain a mailbox on their own. `--all` and a Run `--peek` show at most 100 rows. To drain, repeat plain `check` until it prints `No messages.` (with `--json`, until `messages` is empty); on an older Orca that asks for `--ack <deliveryId>`, ack each Delivery first or `check` returns it again.
- Group addresses: `@all`, `@idle`, `@claude`, `@codex`, `@opencode`, `@droid`, `@grok`, `@cursor`, `@worktree:<id>` — never for `worker_done`.
- Every group except `@worktree:<id>` means the live Dispatches of the sender's own Run, delivered to their Dispatch mailboxes (or child Run mailboxes for nested coordinators). A sender in no Run is refused; `--run` must match the audience and never grants membership.
- Run groups exclude their owning coordinator. A worker raising a blocker sends to `run:<id>`. `@worktree:<id>` includes coordinators in that workspace.
- Quote PowerShell group addresses: `--to "@all"`.

```bash
orca orchestration send --to @all --subject "Heads up" --body "Pausing dispatches for a review."
orca orchestration send --to @idle --subject "Anyone free?"
orca orchestration send --to @codex --subject "Codex workers in this Run only"
```

While a wait is active, the CLI emits small JSON heartbeat lines to stderr every 15 seconds. Stdout remains the final command result.

## Worker contract

Dispatched workers receive a preamble that tells them how to communicate with the coordinator:

- Send `worker_done` exactly once, even on failure, with `--outcome`.
- Include a short `--body` summary: what was done, what was found, and what remains.
- Include both task and dispatch IDs so stale retries cannot complete the wrong dispatch.
- Use `orca orchestration ask` for questions instead of local TUI prompts, then end your turn. Orca wakes you with the answer as mail: in a chat it arrives whole, unless it is too large for one chat message; whenever the wake names a `check` command, run it.

```bash
orca orchestration ask \
  --question "Should I update the shared component or only this page?" \
  --options "shared,page-only"
```

`ask` records the question and returns at once with `pending: true`. Add `--wait` (or `--resume <message_id>`) to block until the answer instead; with `--json`, read it with `jq -r .result.answer`.

## Decision gates

Use `ask` for worker-to-coordinator questions. Use explicit gates when the coordinator has created a task DAG and wants to block a task until a decision is recorded:

```bash
orca orchestration gate-create \
  --task <taskId> \
  --question "Merge the shared button change into the task branch?" \
  --options '["yes","no"]'

orca orchestration gate-resolve --id <gateId> --resolution "yes"
```

## Recovery

```bash
orca orchestration dispatch-show --task <taskId>
orca orchestration dispatch-show --task <taskId> --preamble
orca orchestration task-list
orca orchestration task-update --id <taskId> --status blocked --result '{"reason":"waiting on credentials"}'
```

Reset only when you are intentionally abandoning orchestration state:

```bash
orca orchestration reset --tasks
orca orchestration reset --messages
orca orchestration reset --all
```

`reset` affects runtime-global orchestration state. Do not run it while another coordinator is active unless that is the intended cleanup.

## When a worker ends

- **Settled** means the Dispatch attempt (and, on `worker_done`, its Task) has an outcome: `worker_done` completes (`succeeded`) or fails (`failed`) both. If a terminal worker exits without reporting, Orca fails the Dispatch (returning the Task to `ready`, or failing it if the circuit breaker trips) and mails the coordinator. An `exited` `stopReason` confirms process exit. A `lost` `stopReason` can follow a pane close, restart recovery that could not confirm exit or continuation, or another lost-connection path — inspect `worker-show` before sending mail or retrying, because the original agent may still be running.
- **Ended** means the session is dormant, not destroyed. A finished worker can auto-close while its agent rests unless kept open (`--keep-open` or `worker-keep-open`), without changing the Task's outcome. Records persist. On local Orca and paired servers advertising `orchestration.remote-owned-workers.v1`, `send --to dispatch:<id>` can reuse an eligible open agent, reopen a resumable session, or start a follow-up Task; the receipt says what occurred. Only legacy paired-server attachments refuse `send` with `dispatch_inactive`, in which case start new work with `worker-start --on <server>`.
- **Destroyed** requires proof the process is gone. `worker-stop` settles an unsettled worker only on confirmed stop or exit; otherwise it exits 1 with `stop_unknown` (inspect `worker-show` before acting again). `worker-release` performs post-completion cleanup for a settled worker (and reclaims a live terminal left by a failed start): `release_pending` retries after inventory or reconnect, while `release_unknown` exits 1 — inspect `worker-show` and retry without `--retry-request` (a fresh request ID). The settled-worker sweep releases only proven exits.

Silence, a timeout, or `unverifiable` liveness supplies no proof of exit; a settled Task can still have live or unverifiable resources. `worker-abandon` fences the assignment without killing the process or proving exit. For the full state glossary, run `orca skills get orchestration --reference references/worker-teardown.md`.

## Choosing the right command

Use `orca orchestration send` for a one-way message to another agent. For ordinary mail, a chat receives the whole message with its sender header (a message too large for one chat message gets a note to run `orca orchestration check` instead), Orca never types your words into a terminal agent's input (it reads mail through `check`), and the receipt means the mail was stored, not read. A send to a finished worker's `dispatch:<id>` can instead start a follow-up Task on local Orca or a paired server with `orchestration.remote-owned-workers.v1`; the receipt says which (do not pass `--on` for a Dispatch follow-up). Only legacy paired-server attachments refuse `send` with `dispatch_inactive`; on that refusal, start new work with `worker-start --on <server>`. Use `orca terminal send` for shells, dev servers and REPLs, never to message an agent.

Use `orca orchestration worker-start` (or `dispatch --inject`) when a worker must report `worker_done`, ask questions through the coordinator, and be tracked by task ID.

Use `orca orchestration run-create` + tasks + workers when you want a durable Run namespace and supervised multi-agent loop — not the retired `orchestration run` command.
