Orchestration is Orca's structured multi-agent layer: a **Run** (namespace + coordinator inbox), **Tasks**, **Dispatches**, supervised **workers**, messages, and decision gates.

Use it when you need ownership, completion tracking, or a DAG. For one-off prompts, use `orca terminal send`. For full ownership handoffs without supervision, use worktree/terminal commands from the `orca-cli` skill.

<Callout title="Experimental">
  Enable orchestration under Settings → Experimental before using these commands. The CLI talks to
  the running Orca runtime, so `orca status --json` should succeed first.
</Callout>

<Callout title="Legacy commands retired">
  `orca orchestration run` and `run-stop` (and `coordinator-start` / `coordinator-stop`) perform
  **no effects**. They return recovery text pointing at `orca skills get orchestration --full`. Use
  the Run + worker-start flow below.
</Callout>

## Core model

- **Run** — durable namespace and home inbox. Never schedules or places workers.
- **Task** — a work item with a spec, dependencies, and status: `pending`, `ready`, `dispatched`, `completed`, `failed`, or `blocked`.
- **Attempt** — one execution try for a Task. Retries remain visible as history, but only the current Attempt contributes the Task's default state.
- **Dispatch** — the runtime assignment for one Attempt; it binds lifecycle authority for `worker_done` and heartbeat to an exact worker terminal.
- **Message** — inbox mail (`status`, `dispatch`, `worker_done`, `escalation`, `question`, `heartbeat`, …).
- **Decision gate** — a coordinator-owned question that blocks a task until it is resolved.

Worker completion authority comes from the active Dispatch context. Worker completion and heartbeat messages should include both `taskId` and `dispatchId`. Run completion is separate: only the currently bound coordinator generation can explicitly complete the Run with a summary and evidence.

Task IDs printed in terminals, such as `task_...`, are clickable links. Clicking one asks the Orca runtime for the task's current dispatch and focuses the assigned terminal, including when the task lives in a remote or SSH runtime.

## Maestro Canvas

Maestro turns one workspace's orchestration state into a visual coordination map. Open the fixed
Maestro tab to see Tasks, their current and historical Attempts, Dispatches, terminals, managed
Browser pages, notes, dependencies, and cleanup state without visiting every terminal first.
Terminal and Browser previews load only when their cards need them; opening the Canvas does not
eagerly start every terminal on a paired mobile client.

Use the Canvas to understand and navigate work, not to replace orchestration authority. A Task is
the durable unit of work; an Attempt is one try. A successful retry remains attached to the same
Task and superseded failed Attempts stay available as history instead of appearing as extra failed
Tasks in the default progress list.

Desktop controls:

- Drag empty Canvas space to pan, scroll to zoom, and use **Fit resources** to frame the current map.
- `Shift+scroll` pans horizontally. `Ctrl+scroll`, or `Command+scroll` on macOS, pans vertically.
- Drag or resize cards with their visible controls. Manual positions are preserved; newly discovered
  worker resources are placed near their parent group.
- Click a preview to select its card. Use **Focus** when you want to switch to the underlying Terminal
  or Browser tab.

On mobile, drag in any direction to pan, pinch around the gesture midpoint to zoom and pan together,
and use **Fit** to frame the complete map. Selecting a terminal card loads that one bounded preview;
the full terminal fleet is not started or streamed eagerly. The mobile route uses the paired
desktop/server snapshot and therefore cannot substitute for testing on a physical phone or tablet.

Recovery state is deliberately conservative. `live` and `exited` require evidence from the host
that owns the process. A disconnected SSH host, missing older-client field, timed-out probe, or lost
runtime contact is `unverifiable`, never proof of exit and never permission to retry or clean up a
possibly live resource. Open the affected card for the exact recovery action.

Run completion is an explicit coordinator decision, not an aggregate inferred from resource health.
The Canvas keeps the completion summary, evidence, and any reasoned Task waivers visible beside
Task progress and cleanup warnings. An `unverifiable` resource therefore remains a warning without
blocking completion or being mislabeled as exited. Pending, blocked, or failed deliverable Tasks do
block normal completion unless the coordinator names each Task in an explicit waiver with a reason;
the waiver does not rewrite Task or Attempt history.

The same Canvas model supports local Git worktrees, plain folder workspaces, and workspaces executed
through SSH or another connected Orca server. Orca can launch any configured terminal agent; model
and effort overrides remain limited to the providers named by `worker-start --help`. Clients and
servers update independently, so an older peer may omit optional progress, materialization, Browser,
completion, or liveness detail. Missing fields remain unavailable or `unverifiable`; the client must
not invent a local replacement. An older host may not support `run-complete`; update or reconnect to
a host that advertises the current orchestration contract instead of treating Task totals as a
completion receipt.

For bounded automation, use exact identities returned by Orca:

```bash
orca maestro index --json
orca maestro show --host <executionHostId> --workspace <workspaceKey> --json
orca maestro open --host <executionHostId> --workspace <workspaceKey> --json
```

`maestro show` reports both accepted and materialized node/edge counts. Its exclusion rows explain
superseded Attempt history and workspace-scoped resources instead of silently presenting a smaller
graph. `maestro open` focuses the exact native Canvas; it does not launch a worker or create a page.

## Preferred supervised loop

```bash
orca orchestration run-create --objective "Split checkout QA and summarize blockers" --json
orca orchestration task-create --spec "Audit billing settings for mobile layout" --task-title "Billing audit" --json
orca orchestration worker-start --task <taskId> --worktree current --agent codex --json
# or new worktree:
orca orchestration worker-start --task <taskId> --worktree new-child --name billing-audit --agent codex --setup run --json
# optional per-worker model / effort (Claude, Codex, Cursor only; not with --terminal):
orca orchestration worker-start --task <taskId> --worktree current --agent claude --model <opaque-model-id> --effort high --json
```

`--model` accepts opaque provider model IDs for Claude, Codex, and Cursor. `--effort` requires `--model` and only applies when that agent/model supports the level. Neither flag can combine with `--terminal` (reuse an existing pane). Overrides apply to that launch only and show under `launch.requested` / `launch.effective` in the start receipt. Federated starts need a worker host that advertises launch-preference support.

Wait for completions (process every message in a Delivery, then ack):

```bash
orca orchestration check --wait --types worker_done,escalation,question --timeout-ms 900000 --json
orca orchestration check --ack <deliveryId> --wait --types worker_done,escalation,question --timeout-ms 900000 --json
```

Worker completion (from the worker pane; include injected IDs):

```bash
orca orchestration send \
  --type worker_done \
  --subject "Completed mobile audit" \
  --body "Fixed footer overlap; no follow-ups." \
  --task-id <taskId> \
  --dispatch-id <dispatchId> \
  --outcome succeeded \
  --files-modified "src/app/settings/Billing.tsx" \
  --json
```

`worker_done` requires `--outcome succeeded|failed`.

Complete the Run only after required deliverables are done. Repeat `--evidence` for each concise
proof. A genuinely deferred deliverable needs its exact Task ID and a durable reason:

```bash
orca orchestration run-complete \
  --id <runId> \
  --summary "Implemented the requested flow and verified its contracts." \
  --evidence "Focused orchestration tests passed." \
  --evidence "Typecheck passed." \
  --waive-task "<taskId>=Deferred by the owner to a follow-up." \
  --json
```

Repeated identical completion is idempotent. `run-show` returns the recorded completion. Resource
cleanup is independent: use `run-settle` afterward when the Run owns child worktrees, and follow any
`unverifiable` recovery action without claiming process exit.

Inspect / recover:

```bash
orca orchestration worker-show --dispatch <dispatchId> --run <runId> --json
orca orchestration worker-read --dispatch <dispatchId> --limit 50 --json
orca orchestration worker-stop --dispatch <dispatchId> --json
# After an accepted worker_done: reuse the same terminal for a follow-up Dispatch, or release it
# (archives inspectable output, then closes only that coordinator-owned agent terminal):
orca orchestration worker-release --dispatch <dispatchId> --json
# Keep a settled worker live for debugging when the user asked to retain it:
orca orchestration worker-retain --dispatch <dispatchId> --json
# retry placement is explicit — --retry-of does not inherit --on/worktree:
orca orchestration worker-start --task <taskId> --retry-of <dispatchId> --worktree current --agent codex --json
```

Do not leave completed worker terminals open just to re-read output — use `worker-read` after `worker-release`. Do not substitute a broad `terminal close` when release returns `release_pending` or `release_unknown`; follow the receipt's recovery action.

## Federated workers (optional)

```bash
orca orchestration worker-start \
  --task <taskId> \
  --on windows \
  --worktree new-top-level \
  --repo <exact_remote_repo_selector> \
  --name remote-worker \
  --agent codex \
  --setup run \
  --json
orca orchestration send --to dispatch:<dispatchId> --subject "Follow-up" --body "…" --json
```

Later commands route by Dispatch ID; do not repeat `--on`.

## Low-level dispatch (custom topology)

```bash
orca worktree create --name billing-audit --agent codex --json
orca terminal wait --terminal <workerHandle> --for tui-idle --timeout-ms 60000 --json
orca orchestration dispatch --task <taskId> --to <workerHandle> --inject --json
```

## Messaging notes

- Default `check` is the bound Run's oldest unacked Delivery (FIFO). Replay until `--ack`.
- Process the complete body and payload of every message in that Delivery before acknowledging it.
- A replayed Delivery can include a separate `pendingAttentionMessages` list for newer questions or
  high-priority Run mail. Those rows are not part of the old Delivery and are not acknowledged with it.
- `--peek`, `--all`, and `inbox` do not consume mail. Both `check` and `inbox` accept `--run <runId>`;
  `worker-show` accepts the same Run selector as an identity fence.
- `read: 0` or a missing delivery timestamp does not prove nondelivery: read-only inspection keeps
  those fields unchanged, and a successful `send` proves durable enqueue rather than human attention.
- Group addresses: `@all`, `@idle`, `@claude`, `@codex`, `@opencode`, `@gemini`, `@droid`, `@grok`, `@cursor`, `@worktree:<id>` — never for `worker_done` / heartbeat.
- Every group except `@worktree:<id>` means the live Dispatches of the sender's own Run, delivered to their Dispatch mailboxes (or child Run mailboxes for nested coordinators). A sender in no Run is refused; `--run` must match the audience and never grants membership.
- Run groups exclude their owning coordinator. A worker raising a blocker sends to `run:<id>`. `@worktree:<id>` includes coordinators in that workspace.
- Quote PowerShell group addresses: `--to "@all"`.

```bash
orca orchestration send --to @all --subject "Heads up" --body "Pausing dispatches for a review." --json
orca orchestration send --to @idle --subject "Anyone free?" --json
orca orchestration send --to @codex --subject "Codex workers in this Run only" --json
```

While a wait is active, the CLI emits small JSON heartbeat lines to stderr every 15 seconds. Stdout remains the final command result.

## Worker contract

Dispatched workers receive a preamble that tells them how to communicate with the coordinator:

- Send `worker_done` exactly once, even on failure, with `--outcome`.
- Include a short `--body` summary: what was done, what was found, and what remains.
- Include both task and dispatch IDs so stale retries cannot complete the wrong dispatch.
- Send `heartbeat` messages during long active work.
- Use `orca orchestration ask` for blocking questions instead of local TUI prompts.

```bash
orca orchestration ask \
  --to <coordinatorHandle> \
  --question "Should I update the shared component or only this page?" \
  --options "shared,page-only" \
  --timeout-ms 600000 \
  --json
```

With `--json`, `ask` prints the standard `{id, ok, result, _meta}` envelope, so workers read the answer with `jq -r .result.answer`.

## Decision gates

Use `ask` for worker-to-coordinator questions. Use explicit gates when the coordinator has created a task DAG and wants to block a task until a decision is recorded:

```bash
orca orchestration gate-create \
  --task <taskId> \
  --question "Merge the shared button change into the task branch?" \
  --options '["yes","no"]' \
  --json

orca orchestration gate-resolve --id <gateId> --resolution "yes" --json
```

## Recovery

```bash
orca orchestration dispatch-show --task <taskId> --json
orca orchestration dispatch-show --task <taskId> --preamble --json
orca orchestration task-list --json
orca orchestration task-update --id <taskId> --status blocked --result '{"reason":"waiting on credentials"}' --json
```

Reset only when you are intentionally abandoning orchestration state:

```bash
orca orchestration reset --tasks --json
orca orchestration reset --messages --json
orca orchestration reset --all --json
```

`reset` affects runtime-global orchestration state. Do not run it while another coordinator is active unless that is the intended cleanup.

## Choosing the right command

Use `orca terminal send` for a lightweight prompt to an agent you are watching.

Use `orca orchestration worker-start` (or `dispatch --inject`) when a worker must report `worker_done`, ask questions through the coordinator, and be tracked by task ID.

Use `orca orchestration run-create` + tasks + workers when you want a durable Run namespace and supervised multi-agent loop — not the retired `orchestration run` command.
