---
title: Give your agents web search
---

Agents you launch in Orca run with their own subscriptions and their own tools. Several ship some form of built-in web access, but it isn't always enabled, and it isn't the same as a tool the agent can call on demand. An MCP server closes that gap: define one in a config file at the worktree root, and every agent that reads it gets a live web-search tool.

This recipe uses You.com's hosted MCP server as the example — its free profile needs no account or API key, so every step is copy-paste runnable. Any hosted search MCP works with the same shape: swap in your provider's URL.

## Steps

1. Create `.mcp.json` at the worktree root:

```json
{
  "mcpServers": {
    "you-web": {
      "type": "http",
      "url": "https://api.you.com/mcp?profile=free"
    }
  }
}
```

That's Claude Code's project-scope MCP config — it picks the server up the next time you launch it in that worktree.

1. Cursor reads an `mcpServers` map from `.cursor/mcp.json` at the worktree root. It uses `url` for remote servers (no `type` key — Cursor infers the transport), so copy the block without it:

```json
{
  "mcpServers": {
    "you-web": {
      "url": "https://api.you.com/mcp?profile=free"
    }
  }
}
```

1. Codex doesn't read `.mcp.json`; its servers live in `config.toml` — `~/.codex/config.toml` globally, or `.codex/config.toml` at the project root for trusted projects. The project-scoped file is the better fit here: it travels with the worktree like the other configs:

```toml
[mcp_servers.you-web]
url = "https://api.you.com/mcp?profile=free"
```

1. Check the repo's **MCP Configs** section in settings. Orca inspects `.mcp.json`, `.cursor/mcp.json`, `.claude.json`, and `.claude/mcp.json` at the worktree root and shows each server's name, transport, and status — so you can confirm the search server is wired up before you launch. SSH repos need to be connected first; **Add MCP config** creates an empty `.mcp.json` if the repo has none.

1. Launch an agent in the worktree and ask something that needs the live web — "what changed in the latest release, and what's the migration path?" The agent calls `you-search` instead of guessing from training data.

## Keys stay out of the repo

The example profile is deliberately keyless, so it's safe to commit. If you use an authenticated MCP server instead, don't put its API key in a committed `.mcp.json`. Keep keyed servers in the agent's user-level config — `~/.claude.json` for Claude Code, `~/.codex/config.toml` for Codex, `~/.cursor/mcp.json` for Cursor — and leave the keyless server in the project file. Note that if the same server name appears in both a project file and the user-level file, the project configuration wins (Cursor and Claude Code both resolve duplicates that way), so a keyless project entry will shadow — not merge with — a keyed global one.

## Why it works

Orca doesn't broker the MCP connections — each agent reads its own config files and connects itself. Orca's part is visibility: the MCP Configs section reads the same files the agents do, so what you see is what they get. And because the config is a checked-in file, every worktree you cut from that branch starts with the same servers.
