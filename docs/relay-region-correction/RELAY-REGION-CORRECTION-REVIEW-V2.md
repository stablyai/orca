# Independent review of region-correction plan v2

Verdict: **REVISE**. Retaining physical connections is a sounder and smaller direction than proving global idle. The plan correctly limits its user promise and identifies many necessary tests. Before implementation, make retained-source renewal and rollback concrete; current recovery cannot simply be reused unchanged.

Reviewed 2026-09-10 against freshly fetched `origin/main`, immutable commit **33436c30d89154948013c462b74419eb748980a1**. All source references below mean that commit, not worktree HEAD or the diagnostic snapshot. Fetch advanced beyond the revision supplied in the review request. `git diff` from the experiment revision `721a2692893ab29f8daee3149965bf5e9adf99a0` shows no changes in the desktop relay or cloud relay source paths; the mobile transport changes concern runtime capability advertisement. Thus the cited lifetime mechanisms remain current.

## Severity-ranked findings

### P1 — Specify retained-source control renewal; auth refresh does not renew this lifetime

**Current source:** `src/main/runtime/relay/relay-origin-pool.ts:77` refreshes authorization on all origins, but `:241-261` schedules/rebinds only the active origin. `cloud/apps/relay/src/host-session-registry.ts:174-175` gives a control a six-hour lifetime with thirty-minute jitter; `:1093-1094` updates JWT identity without extending that lifetime. `:1183-1185` sends an unqualified zero-grace drain and closes an expired control. `:1064-1070` subsequently closes its splices on orphan expiry. Pool `:130-138` only recovers an active origin's control close.

**Scenario:** a healthy, authenticated source connection survives the proposed optional 30-second deadline, but its source control reaches its original lease expiry after the target becomes active. It is deliberately disconnected by the lease/orphan path. This can happen shortly after migration if the source was already near expiry. It is not explained by the plan's auth-expiry exception. The one-hour store experiment renews database activity rows directly and never exercises this control lease.

Simply rotating every origin is insufficient. Cell `host-session-registry.ts:727-745` checks the current assignment and excludes `drain-only` from same-generation rebind. `assignment-store.ts:3179-3192` accepts only the current target cell/epoch. A source renewal therefore needs authority derived from the open migration, and must preserve the generation and its drain-only admission status.

**Smallest correction:** choose and document one negotiated renewal mechanism for retained sources, using the existing control lifecycle where possible. If using rebind, authorize only the exact open attempt/source incarnation/epoch/session generation with the existing resume proof, renew its lease without reopening new admission, and schedule it independently of target rotation. Alternatively specify an equally fenced lease extension on the existing control. Do not weaken ordinary assignment validation or auth enforcement. Add a real cell/desktop protocol test with the source already near expiry and another crossing multiple control leases, including renewal failure and retirement racing renewal.

This is a missing concrete implementation contract, not a claim that v2 explicitly proposes dropping renewal. Its instruction to “retain both controls' auth/lease renewals” currently assumes a source renewal path that does not exist.

### P1 — Assignment rollback must restore the retained generation, not use fresh-generation recovery

**Current source:** generic expired-migration rollback can write a new source assignment epoch and abort the migration (`cloud/apps/relay/src/assignment-store.ts:6719-6773`). That does not clear cell `regionalDrainAttemptId`. Auth refresh explicitly leaves a regional source drain-only (`host-session-registry.ts:1094`), and new clients require an active source session (`:275-288`). Rebind excludes drain-only (`:741-747`); fresh-generation activation closes the old splices (`:935-947`). Desktop same-cell rebind failure falls back to fresh activation (`relay-origin-pool.ts:179-187`). If the target was already active, recovery toward the source also creates a new origin rather than selecting an existing retained origin (`:195-196`, `:221-224`).

**Scenario:** the source has a quiet live client; target registration fails and durable expiry rolls assignment back. New clients reach the source but its old session still rejects admission. When desktop follows the rolled-back assignment, ordinary recovery can create a new generation and kill the very connection optional optimization promised to preserve. The same reuse hazard exists if an active target fails and recovery selects the retained source. The generic rollback path does not universally require zero source activity; the separate 24-hour regional abort path does (`assignment-store.ts:6487`). Those paths must not be conflated.

**Smallest correction:** define a retained-source rollback transition, fenced by attempt and exact source generation, which atomically/recoverably transfers assignment authority and clears only that optional drain. Reuse the existing retained origin on desktop. Preserve source data and basis ownership while updating assignment metadata. A delayed drain for the aborted attempt must not re-enter drain-only; a delayed target registration must not overturn the newer source epoch. Define target reservation cleanup and the point at which a new optional move is permitted. This needs durable replay, not an in-memory “cancel drain” alone. If preservation is not possible for a specific failure, state that narrower recovery outcome explicitly instead of relying on “existing recovery.”

Test target never registered, registration committed with lost acknowledgment, target failed after activation, and rollback concurrent with source final release. Include a mutation whose acknowledgment crosses rollback. No pre-move idle protocol is necessary.

### P2 — Name the mode-specific durable lifetime and rollback floor before promising indefinite retention

**Current source:** `cloud/apps/relay/src/assignment-store.ts:355` sets a 24-hour maximum refresh age; `:6160-6167` stops refreshing at that age and separately limits unregistered targets to five minutes. `:6423-6435` selects aged attempts for abort. `:5250-5311` continually redrains receipted, registered, still-active sources after grace, with zero grace and a send cap. These are additional duration-dependent paths beyond the two diagnostic timer removals.

**Scenario:** a healthy connection lasts longer than a day. The v2 promise requires continuing migration authority/accounting, but “reuse existing leases” stops at 24 hours. Merely preserving mode in the redrain payload also leaves a successfully draining long session consuming unnecessary dispatches and potential failure budget. An older director operating the new durable rows would still run these old age/redrain selectors because it does not know the new mode.

**Smallest correction:** explicitly exempt healthy optional retained-source attempts from the registered 24-hour refresh ceiling and age-only redrain lane, while retaining bounded target-registration failure/reconciliation. Define cleanup from authenticated generation release or failed-source recovery rather than age alone. Keep emergency mode unchanged. Establish a minimum compatible director/worker rollback revision before enabling this mode; disabling starts is insufficient to make older reconciliation code compatible with open attempts. Either deploy a compatibility floor first or prohibit rollback below it while such attempts exist. Preserve durable mode on retry and recovery, including control rebind.

The plan already recognizes replay, hours-long retention and rollback tests. This finding asks it to name these specific existing mechanisms and their intended replacement predicates. It does not claim that the current 24-hour abort forcibly closes a healthy source by itself: that path waits for source activity to disappear.

## Reviewed obligations already covered adequately by the plan

- **Retirement callback:** there really is a missing notification. `relay-origin-pool.ts:123-127` retries retirement on connection release; `:286-294` refuses while control requests remain. `relay-control-requests.ts:164-167` and `:178-183` remove completed/timed-out requests without notifying the pool. V2 explicitly requires the final completion/timeout event. Implement one pending-work-change notification, including rejection and close, rather than polling. A callback only on successful RPC response is insufficient.
- **Admission race:** cell `host-session-registry.ts:275-279` checks active state before awaiting activity acquisition at `:307`; it later inserts pending work and sends conn-open at `:348-355`. Source retirement can intervene. V2 explicitly requires a final session/generation check and tracked pending attaches. Define the local admission linearization point and release any acquired reservation on failure. Do not count a desktop map alone as proof that the cell has no accepted work in flight. This is local lifecycle fencing, not the rejected distributed idle gate.
- **Capabilities:** stale app-version or measurement reports cannot authorize a replacement generation. Use the authenticated source control's negotiated support and bind claim/dispatch to that generation and current cell incarnation; recheck on receipt. Couple rejection after assignment claim to the rollback transition above. The plan identifies this requirement, but the wire/schema review must supply the actual fields and transaction order before enable.
- **Ordering:** server-issued windows, fixed expiry, incumbent epoch, successor invalidation and inconclusive tombstones address the stated stale-result problems. Preserve server-generated order across restarts and do not let a legacy write refresh verified evidence. Same-generation conflicting outcomes must fail closed. The missing concrete schema is acknowledged, so I found no additional source-proven flaw in that proposed protocol.
- **Capacity/fairness:** the conservative bound below the ten-row work page is a reasonable initial constraint only if it is a locked global bound counting pre-existing open work, and waiting rows do not bypass it through another writer. The hundred-row lease refresh is oldest-first (`assignment-store.ts:6120-6124`). Test an older saturated page with eligible newer work. Excluding optional healthy waits from age redrain also avoids avoidable worker competition. Never use expired splice leases to erase real source capacity.
- **Compatibility:** explicit opt-in is necessary for strict schemas. Keep old request/response behavior when opt-in is absent, and test both request rejection and response negotiation fallback. The new durable-mode rollback floor is distinct from desktop/cell wire fallback.
- **User experience:** the physical-connection definition, delayed benefit for continuously open connections, and mobile's scheduled rather than guaranteed background deadline are appropriately cautious. No fresh pairing or typical downtime claim is justified by the simulated 251ms result. Keeping the source transport avoids deliberate migration replay of a sent mutation; real-socket validation must still establish application behavior.

## Minimal next plan

1. Keep the proposed architecture and disabled controls. Add a compact state table for optional source retention, control renewal, target registration, rollback, final release and obsolete replay, with exact identity/authority at each transition.
2. Specify the retained-source lease mechanism and same-generation rollback above. Make the durable 24-hour/redrain predicates mode-aware and establish the compatible rollback floor.
3. Implement the existing pending-work notifications and local admission fencing, then negotiate the mode through existing protocols. Do not revive an idle detector or merge the diagnostic timer deletion.
4. Validate near-expiry and multi-day retention; failed/ambiguous target registration; active-target loss; delayed drain after rollback; pending RPC final completion; two clients plus late attach; emergency drain; and old/new versions. Use actual WebSocket traffic and separate Postgres concurrency tests on **55440 only**, with explicit executed counts. The existing fake-socket/SQLite evidence remains a useful baseline, not acceptance evidence for these cases.

**REVISE**, with no implementation or production action authorized by this review.
