## Findings and clarifications

### No outstanding P1/P2 implementation-plan blocker

The plan now specifies the important choices that earlier versions deferred: server-issued ordered windows; actual assignment basis; explicit negotiated retention; first validated short grant; fencing of successful and failed asynchronous completions; same-generation source rollback; mode-specific multi-day lifetime; shared concurrency accounting; and a compatible director/worker rollback floor. These are concrete contracts against which code can be reviewed. Asking for all of that code and its passing tests before approving implementation would confuse design readiness with deployment readiness.

### P3 — Cold-start sequencing clarification incorporated during review

The plan correctly separates legacy placement hints from migration eligibility and says initial placement may choose the best measured region. Preserve that distinction in the actual request sequence. Current startup probes concurrently with authorization, then sends the resulting hint in its first assignment request (`src/main/runtime/relay/relay-session-broker.ts:202`, `:214`). Placement defaults to `preferredRegion ?? RELAY_DEFAULT_REGION` (`cloud/apps/relay/src/assignment-store.ts:803`); a successful sticky request returns its current assignment rather than moving to a newly reported hint (`:666`, `:736`).

Concrete regression to avoid: a first-time desktop uses an unhinted `/v1/assign` solely to obtain the new measurement window. That request commits default-region placement before the probes run. Sending the later best-region report does not itself undo the sticky assignment, and correction may be disabled or unsupported. This would make new-user placement worse while introducing a feature intended to improve it.

**Smallest clarification:** preserve the current pre-assignment probe as a placement-only hint, including on updated desktops. The first assignment may also return an opt-in window bound to the actual resulting assignment; only probes taken after receiving that window may certify migration. Do not turn the earlier placement sample into window-certified evidence. Existing assigned desktops may refresh through the window flow without making that optional exchange a prerequisite for keeping a healthy control. This follows the existing plan's separation of placement and migration; no new endpoint or placement engine is required. Add a first-ever-host test with correction disabled, a hint/actual-placement mismatch, and old-server fallback. This was a nonblocking clarification of the intended design, not evidence that the plan mandated the broken sequence. Before finalizing this report, I reread the coordinator’s new section 1 paragraph: it now explicitly preserves pre-placement probing/hints, requests the window with or after assignment, requires post-window migration measurements, and adds cold-start/fallback tests. The clarification is resolved.

### P3 — Treat section 5a as normative and retire the historical review labels

Section 5's instruction to “define when” source admission returns is now answered by section 5a: a durable newer source epoch, aborted-attempt tombstone, exact retained-generation reconciliation, and authority validation before admission. Its generic recovery language must not override that contract. Similarly, section 4's nominal transition must include section 5a's valid first grant before retained-mode acknowledgment/cutover. ## Whole-plan assessment against current source

**Decision ordering, expiry and scheduling — coherent.** Current preference storage uses receipt-time hints, and current caches contain no server decision generation (`cloud/apps/relay/src/assignment-store.ts:669`; `src/main/runtime/relay/relay-region-preference.ts:44`). Sections 1–3 replace that authority model with a persisted per-host generation, fixed server expiry, assignment epoch/region, policy and outcome. Successor issuance invalidates older evidence; an inconclusive tombstone cannot be upgraded by a conflicting duplicate. Delayed reports, restarts and legacy omission therefore have defined conservative outcomes. Reports must commit against the current assignment under the claim lock. Exact columns, atomic generation allocation, retry encoding and lock ordering remain normal first-phase design/code review, explicitly required by section 1.

The broker-owned single-flight task and deadline address the real missing refresh path: current auth refresh only refreshes origin authorization (`relay-session-broker.ts:252`), and control rotation reuses the assignment (`relay-origin-pool.ts:237`). Reusing a window for report retries, separating retry time from eligibility expiry, discarding stale responses and applying unchanged assignment metadata without rebind prevent avoidable auth coupling and reconnect churn. Implementations must coordinate startup, normal refresh, drain recovery and resume through that same owner, not create an independent report loop. Positive jitter may leave a brief ineligible interval; it must never extend the server expiry. That is safe deferral, not stale eligibility.

**Thresholds and adoption — appropriately bounded claims.** Current hysteresis compares the prior preference (`relay-region-preference.ts:305`), using both 25ms and a 0.8 ratio (`:317`). The plan correctly applies those existing margins to the measured assigned region and epoch, while treating missing measurements as ineligible. It does not claim these constants are empirically optimal. Current candidate selection is already bidirectional (`assignment-store.ts:5328`), so no second migration engine is justified. Version-bearing close logs cannot certify the active source socket; the plan instead requires current authenticated generation/cell-incarnation capability binding. Sampled comparative evidence and application reliability measurements remain necessary before fleet benefit claims.

**Forward retention and retirement — sound reuse, with explicit local fencing.** Existing origin ownership already routes basis-bound control work to the source (`relay-origin-pool.ts:58`) and visits all origins for auth refresh (`:77`). Target activation currently installs the unwanted deadline (`:215`, `:275`). The cell independently installs another deadline (`cloud/apps/relay/src/host-session-registry.ts:681`). Mode-aware changes at both ends are necessary and expressly planned; deleting only those timers is insufficient.

Allowing already-admitted source connections to finish removes the need to prove distributed idle. The remaining local admission/retirement race is real: cell admission checks the session at `host-session-registry.ts:275`, awaits acquisition at `:307`, then inserts pending work at `:348`. Sections 4 and 5a require the final session/generation check and abandoned-reservation release. Desktop retirement already waits for pending requests (`relay-origin-pool.ts:286`), but request completion/timeout currently lacks the final notification (`relay-control-requests.ts:164`, `:178`). The plan explicitly requires response, rejection, timeout and close notifications. These are acknowledged implementation obligations, not newly discovered blockers.

**Source renewal — the smaller mechanism is defensible.** The cell already requests activity renewal from the heartbeat (`host-session-registry.ts:1097`). The store's single Postgres statement locks assignment, authorizes the exact forward migration and updates only the named control (`assignment-store.ts:3355`, `:3381`). Reusing a successful request's original 105-second horizon to extend the retained control avoids another recurring desktop protocol. First-grant adoption must reject an already-expired success and must not pause normal expiry while waiting. Security and silence closure remain independent (`host-session-registry.ts:1173`). Short grants protect healthy ongoing retention; they do not guarantee continuity through arbitrary database/network failures.

The final correction correctly extends fencing to scheduling changes, denials, reacquisition and post-await continuations. Current denial handlers can close the mutable session socket (`host-session-registry.ts:1124`, `:1161`); current missing-activity recovery awaits acquisition (`:1130`). A late retained-attempt denial after rollback must not close the restored authoritative source, while a current applicable denial still must enforce authority. The plan now states both halves. It also disallows the current-assignment SQL alternative (`assignment-store.ts:3373`) from bypassing an aborted retained attempt and preserves assignment → attempt → migration → activity dependencies used by rehome refresh (`:6133`). No additional recurring query is necessary.

**Rollback and failure recovery — sufficiently concrete to implement.** Ordinary desktop recovery can create a replacement origin (`relay-origin-pool.ts:179`, `:221`); ordinary cell fresh-generation activation closes existing splices (`host-session-registry.ts:935`). Generic durable rollback alone changes assignment and aborts migration (`assignment-store.ts:6757`) without restoring the retained session. Section 5a explicitly replaces reliance on those defaults with a durable idempotent rollback, exact source reuse and late-target fencing. The transition table covers target never registering, target failing after activation, source loss, final release and obsolete messages without authorizing a third overlapping optional rehome. Its source-gone fallback does not pretend preservation remains possible. The planned ambiguous-registration and rollback races must establish these transitions in code.

**Lifetime, capacity and cleanup — correctly treated as one feature.** Existing registered refresh stops after 24 hours (`assignment-store.ts:6160`), and zero-grace redispatch explicitly tries to close still-active sources (`:5245`). Sections 5/5a require mode-aware exemptions, bounded unregistered-target recovery, both generic and regional cleanup, and a compatible worker floor. Current completion waits for source activity removal (`:6279`); renewal and retirement must remain consistent with that authority/accounting lifecycle. Neither expired splice leases nor duration alone can become an optimization idle verdict.

The existing oldest-first 100-row refresh (`:6117`) and ten-row candidate page (`:5372`) justify the planned conservative globally locked concurrency cap and fair traversal. Counting pre-existing work, filtering before LIMIT, retaining source costs plus target reservations and separating healthy waiting from dispatch failure are necessary. Indefinite individual retention can occupy an optimization slot indefinitely; the design knowingly trades correction throughput for connection preservation. That is not unbounded concurrent allocation or permission to force completion.

**Compatibility, deployment and validation — adequate plan, outstanding execution.** Both assignment schemas are strict (`cloud/packages/relay-contract/src/director-messages.ts:13`, `:24`), and current HTTP 400 fallback only removes known legacy fields (`src/main/runtime/relay/relay-http-client.ts:200`). Explicit opt-in request/response negotiation and fallback are therefore required. Durable-mode compatibility is separate: old workers can reinterpret rows even with new claims disabled, so the section 5a rollback floor must be deployed across all participating workers before enable. Server/database support, cells and desktops can ship gated; actual capabilities, not release availability, govern eligibility.

The validation plan covers real WebSockets, delayed mutation acknowledgments, independent execution/output, two clients and quiet connections, mobile resume, pending admission, failed registration, multi-day retention, concurrency and mixed versions. Mobile currently schedules background grace and checks overdue suspension on foreground (`mobile/src/transport/mobile-relay-background-grace.ts:106`, `:124`); it does not establish a guaranteed server-observed disconnect or reconnect duration. SSH execution ownership and folder workspaces remain transport-independent concerns, correctly preserved by the plan.

The timer-removal tests establish a causal deadline mechanism; the one-hour SQLite test establishes only its simulated store scenario. The renewal prototype injects authorization that the feature has yet to negotiate. Its 43 registry tests/typecheck and six PostgreSQL 17 tests are useful narrower evidence; the current real-PG test starts an ordinary evacuation and directly completes its migration (`cloud/apps/relay/src/control-renewal-postgres.test.ts:255`), not the future mode. Implementation validation must use prescribed PostgreSQL 16 on isolated port **55440**, executed counts without conditional skips, and the actual mode/rollback concurrency predicates. Real traffic across the old lease boundary and multi-day cleanup remain release gates. Numerical regression limits and sample sizes belong before authorized production enable, as section 6 already requires.

**Final decision: READY TO IMPLEMENT; NOT READY TO DEPLOY.** Preserve the cold-start placement path, apply section 5a consistently, and execute the plan's already-specified staged implementation and validation. No additional architecture redesign is warranted by this review.
