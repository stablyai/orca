## Severity-ranked findings

### P1 — Fence failed renewal completions across retained-generation rollback too

The plan's section 5a and `RETAINED-CONTROL-LEASE.md:13` explicitly guard **success** handling against obsolete attempts, socket replacement and rollback. The prototype does that around expiry extension, but retains the existing rejection handler unchanged (`retained-control-prototype.patch:20-42`, SHA-256 `3fa262216fa02499edea0122318dfc8aac6686b2c82aede6855bbd5151a32f2b`).

At the immutable source pin, `cloud/apps/relay/src/host-session-registry.ts:1124-1128` closes `session.socket` on an authority denial without checking the captured request's attempt, socket or completion order. The moved-activity branch does the same at `:1161-1163`. The missing-activity branch at `:1130-1155` checks only current session existence/state/socket before reacquiring, and its post-await denial can likewise close the current socket. Successful callbacks alone use `activityRenewalCompletedAttempt` (`:1120-1122`).

**Concrete scenario:** retained attempt A has a renewal in flight. Durable rollback aborts A and restores the source assignment; the cell applies the supported same-generation rollback and preserves its socket and splices. A's mode-bound renewal then evaluates against the aborted attempt and is correctly denied, or its already-produced denial arrives late. If that denial follows today's authority-error handling, it closes the now-authoritative preserved source. The more precise proposed SQL predicate makes this a normal obsolete-attempt result, not evidence that the socket's current authority has been lost. Similarly, a delayed missing-activity result must not start recovery on behalf of an obsolete attempt.

**Smallest correction:** make the existing “ignore obsolete renew” transition explicitly apply to every renewal completion and its recovery continuation. Before changing scheduling state, closing a socket or initiating reacquisition, validate captured session, socket, activity ID and the local authority/mode transition identity. Recheck after awaited recovery; clean up an abandoned acquired lease as appropriate. A stale retained-attempt denial must be discarded or trigger current-authority reconciliation, never directly close the preserved socket. Current, applicable authority denial must still enforce closure. Keep ordinary behavior unless the captured lifecycle has become obsolete.

Add controlled-promise cases for delayed authority denial after rollback, delayed denial after a newer valid renewal/authority transition, obsolete missing-activity recovery, and an applicable denial that still closes. Assert preserved socket/splice identity as well as no lease extension. The existing obsolete-attempt test only resolves success; the existing authority-loss test rejects while the attempt is still current.

This is a specific refinement of the already documented rollback/stale-transition obligation, not a request to design rollback again. It blocks treating the callback prototype as a sufficiently fenced implementation; it does not invalidate heartbeat reuse.

## Mechanism assessment

- **Expiry and security:** `max(previousExpiry, requestStart + 105s)` extends only as necessary and never adds a fresh six hours. Keeping an already-authorized ordinary lease is intentional. The store validates requested bounds at `assignment-store.ts:3317-3327`, and uses `GREATEST` at `:3382-3383`. JWT, silence and local lease closure remain independent at `host-session-registry.ts:1173-1185`. Request-start deadlines avoid manufacturing a new horizon from slow response delivery. The first-grant consumer must still reject a grant whose deadline is already past when adopted; a successful old database operation is not a currently valid first grant.
- **First grant:** the revised ordering addresses the actual race: heartbeat launches renewal asynchronously before checking local expiry (`host-session-registry.ts:1107-1119`, `:1183-1185`). Obtain and apply a valid initial grant before acknowledging retained-mode readiness/cutover, with the documented current-session check. Do not suspend expiry while awaiting it. The one-millisecond negative test demonstrates the problem; it does not test the future adoption path.
- **Authority:** the existing Postgres statement locks assignment, exact forward migration, then activity (`assignment-store.ts:3355-3387`). It rejects missing and wrong-kind/cell activity and does not insert a replacement. Narrowing this statement for retained mode is the right reuse point. The current-assignment authorization alternative at `:3373` must not accidentally authorize a retained-mode request for an aborted attempt after rollback. Separate the ordinary authorization branch from the retained-mode branch; no additional recurring query is needed.
- **Lock ordering:** the present renewal has no attempt-row lock. Existing rehome refresh/abort lock assignment, attempt, then migration (`assignment-store.ts:6133-6147`, `:6450-6464`). If the new predicate locks the attempt, express that same dependency order before migration and activity in the single statement. Merely appending an attempt join is not proof of lock order. If immutable fields are copied onto the migration instead, review all outcome transitions under the assignment lock. I found no concrete new deadlock in the proposal as written; its exact SQL and concurrency proof remain acknowledged implementation work.
- **Missing activity and liveness:** reacquisition alone must not extend the in-memory lease. A subsequent validated renewal can do so while time remains. Healthy 30-second renewal against a 105-second horizon has room for delayed/missed cycles, but cannot promise survival through arbitrary database stalls. Current due-at scheduling allows another request on later heartbeats while an earlier one is unresolved (`host-session-registry.ts:1107-1122`); the exact two-calls-per-four-ticks evidence describes successful steady state, not a universal concurrency bound. No extra desktop timer is justified by these limitations.
- **Emergency drains:** `host-session-registry.ts:652-658` sets the global drain flag and schedules close independently; the prototype refuses extensions while that flag is set. Keep that behavior and invalidate optional-mode identity for any overriding per-host forced drain. The existing test exercises global emergency drain, not every future mode transition.
- **Rollback and long duration:** same-generation restoration, desktop origin reuse, mode-aware 24-hour cleanup/redrain, capability binding and the compatible operational rollback floor are already explicit required contracts. They should not be relabeled as newly discovered design defects. The renewal change alone proves none of them. SSH execution ownership and folder-versus-worktree identity do not alter this transport lifetime mechanism.

## Evidence limits and required next proof

The documented 43 registry tests, package typecheck and six executed Postgres tests are useful evidence for the limited claims made. I inspected their source and patches but did not independently rerun them. The 12-hour simulation repeatedly extends a deliberately shortened initial lease with mocked grants and synthetic sockets. It demonstrates callback behavior and steady-state call counts, not real device retention, durable mode authority, rollback, or traffic continuity.

The real Postgres test at the pin uses `startEvacuation` and then directly completes its migration (`cloud/apps/relay/src/control-renewal-postgres.test.ts:255-280`). It validates the current forward-migration primitive; it cannot validate nonexistent optional-mode predicates or attempt lock ordering. The evidence note expressly says this, so I do not find an overstated full-feature claim. Its run used PostgreSQL 17; relay-ops calls for PostgreSQL 16. Keep the run labeled accurately and include the prescribed version in implementation validation rather than presenting it as that version's proof.

Next, add the failure-completion fencing contract above, then implement and test the already-listed integration requirements. Acceptance needs initial-grant ordering, mode-bound SQL with actual Postgres concurrency, rollback and late responses, successful missing-activity recovery within a valid horizon, normal versus optional versus emergency mode, and real socket traffic across the old lease boundary. Use isolated local Postgres on 55440 with explicit executed counts and no skipped-pass claim. No larger renewal protocol or second recurring loop is warranted.

**REVISE the completion-fencing detail; approve the heartbeat-reuse direction. Production implementation remains unapproved and incomplete.**
