# Explicit project teams

**Opt-in:** Place `project-teams.json` in the active Orca profile. Repository files and installer bundles do not automatically enable teams. The registry contains `{ "version": 1, "teams": [{ "config": "team.json", "projectRoot": "/absolute/project", "enabled": true }] }`. Relative config paths resolve beside the registry. The project must already be imported on the local host; SSH and WSL execution are not inferred from a local path.
**Role configuration:** A team file contains `{ "version": 1, "name": "Review team", "roles": [{ "id": "reviewer", "title": "Reviewer", "provider": "codex", "model": "your-model", "effort": "medium", "cwd": ".", "instructions": ["reviewer.md"] }] }`. Role IDs and titles must be unique. Instruction and settings resources must stay beneath the team file's directory. Claude roles additionally require an explicit account, config home and tools selection; the launcher verifies the account through the CLI before starting.
**Execution:** `project-team-startup.ts` loads the profile registry after runtime startup and calls `ProjectTeamService`. The service resolves the current workspace, checks existing panes using the host runtime, and starts missing roles through `terminal.create` with focus disabled. It does not overwrite settings or claim the model has completed its initialization. The runtime report records `started`, `present` or `blocked` and current terminal handles.
**Preservation:** Existing active or unverified work is left alone. A proven empty shell can be replaced in its saved pane only after the role files and launch arguments have been validated and the runtime confirms the shell stopped. Concurrent loads coalesce. An uncertain creation retries the same mutation ID during the process lifetime. Disabling a binding stops automatic starts; it does not kill an existing agent.
**Validation:** `project-team-service.test.ts`, `project-team-launch.test.ts` and `project-team-pane.test.ts` cover bindings, resources, concurrency, saved panes, lost replies and launch parameters. `tests/e2e/project-team-startup.spec.ts` exercises profile registry loading, folder workspace lookup and real terminal creation with a deterministic fake CLI on Windows. It does not contact a model or use a real account. Changes to startup ownership or launch arguments must rerun these cases.
**Limitations:** The initial registry must exist at application startup. Provider CLI versions and account validity can block a role; errors do not authorize permission changes. This is desktop-local only; real model turns, SSH/WSL and macOS/Linux process launch are not covered by the Windows integration. Role identity currently uses the saved title; renaming roles needs manual review. Restart recovery relies on the existing persisted terminal inventory; the in-memory mutation map is not a new persistent task ledger.

**Review regressions:** Validated resource paths are passed unchanged to Claude. A malformed team produces a per-team error and does not block later teams; name bindings accept local folder workspaces without hostId. Unit coverage exercises both branches. The hidden Windows CLI test asserts the actual tab and exactly one launch; its deliberately unrecognized fake child must be blocked with team_existing_role_requires_attention on reload, never replaced. Recognized active-agent present behavior remains covered by service tests.
