# Opt-in agent question routing

**Scope:** This follow-up depends on the Work Inbox CLI/MCP interface. Add `ORCA_WORK_INBOX_ROUTING=1` to a local Codex or Claude agent's launch environment to attach the built-in question tools and routing instructions. Existing launches without this value are unchanged. This does not turn native provider permission requests into approval, change account configuration, or restart existing terminal processes.
**Terminal flow:** The common `spawn-options-assembly.ts` calls `prepareAgentWorkInboxLaunch`. It keeps the existing Codex no-daemon preparation and skips SSH/WSL routing. Claude receives a profile-private MCP config; Codex receives invocation-only MCP config and effective developer instructions read from its selected configuration. Caller identity is passed at launch, never saved to an agent home.
**Native chat flow:** `claude-work-inbox-options.ts` merges existing prompt, MCP servers and allowed tools without granting shell or file permissions. Codex adds the MCP launch arguments, opens/resumes its thread, and appends a routing message before accepting user work. An opted-in provider that cannot preserve its instructions or rejects the required method fails startup; it does not silently claim routing is active.
**Question contract:** An agent supplies an immutable request ID, retains the returned question ID on timeout, waits on that ID, and acknowledges an answer before continuing. Closing a question returns cancellation with no answer and is explicitly not approval. The original account, conversation, tool restrictions and execution host remain authoritative.
**Tests:** `work-inbox-launch.test.ts` covers generated shell arguments, option boundaries, caller identity, remote exclusion, opt-in behavior and instruction preservation. `codex-work-inbox-session.test.ts` covers fresh/resumed native sessions and rejection. The Claude stream connection suite inspects actual SDK child argv. `tests/e2e/work-inbox-mcp-launch.spec.ts` launches the generated MCP command against a disposable Electron profile, asks through stdio, closes the visible question via CDP, and receives cancellation through the same MCP client. Existing Codex isolation and MCP tools suites are adjacent regressions.
**Known limits:** Only local Codex/Claude launches are configured here. This does not attach tools to an already running terminal, inject prompts into every other provider, or configure an older remote peer. Real model turns are not needed by the isolated contracts and are not claimed as tested. A local Codex app-server was additionally checked with an empty home for config/read, thread/start and thread/inject_items without starting a model turn. Native Linux/macOS, SSH and real Claude login remain separate validation.
**Coverage correction:** The existing Codex identity assertion assumed a POSIX CLI filename and rejected Windows drive paths and `.cmd` shims. That failure was reproduced on the unchanged inbox base before correcting the platform-specific assertion. Launch/routing changes must run the named source, SDK and MCP integration cases.

**Late native-chat answers:** `workInbox.answer` commits the human answer in the existing inbox store, then wakes an active ask. If no ask remains, `work-inbox-chat-delivery.ts` sends the answer to the original session through `sendAgentTurn` and the existing durable session operation ledger. The operation ID is stable for that question revision, so retries do not start duplicate turns. A busy chat queues the answer. Provider acceptance or the agent acknowledgment marks delivery; queue admission alone does not. A missing/refusing chat leaves the saved answer unacknowledged and returns an error. Closing without answering does not start a chat or grant approval.
**Acceptance matrix:** Desktop answer → runtime human-caller check/CAS → live ask or original session send → journal/provider acceptance → inbox receipt. `work-inbox-chat-delivery.test.ts` uses real disk SQLite and the real session host/journal with a scripted adapter: one-hour-old question, expired wait, original-session delivery, retry deduplication, busy queue, missing host, forged answer and closure. `tests/e2e/work-inbox-chat-resume.spec.ts` uses hidden Electron and the existing Claude protocol stub, verifies the original chat receives another reply after its ask timed out, and uses no real account. The hour is simulated in the host test; the UI test exercises an expired wait, not an hour of wall time.
**Review boundaries:** Terminal identity omitted from a launch overlay can be inherited from its provider, while a native session explicitly clears unrelated terminal identity. Codex opt-in terminal routing refuses PowerShell and cmd before launch because their native quoting is not verified to preserve developer instructions; use native chat or a POSIX terminal. This refusal does not change ordinary launches with routing disabled. Windows native chat is covered by the hidden integration; real model behavior and native OS IME remain separate validations.
**Coverage gap:** Earlier tests stopped at receipt of an MCP answer and never ended the original waiting call before answering. They could not detect a saved answer with no running consumer. Inbox answer/receipt, native send admission and session restart changes must exercise the late-answer cases above. A retired or unavailable original chat is never replaced with another session automatically.

**Return to the asking agent:** Selecting an option keeps the question open. After Send answer succeeds, `WorkInboxSheet.tsx` closes the inbox and `open-work-inbox-agent.ts` uses the existing `openAgentMessageSender` host lookup and chat/terminal activation flow. The question's execution host owns the lookup, including folder workspaces and remote targets; the active desktop host is not substituted. Missing or unreachable agents use the existing navigation feedback without changing the saved answer. A conflict, failed submission, closed inbox or changed host does not navigate. The hook tests cover those submission boundaries, existing sender tests cover host ownership and unavailable/legacy peers, and `work-inbox-chat-resume.spec.ts` switches to another terminal before answering and verifies the original chat becomes visible automatically. `work-inbox-close-reopen.spec.ts` still verifies the saved answer and receipt after reopening the inbox. Native OS window activation and live SSH execution are not claimed by these hidden-renderer tests.
