## Conditional worktree removal

`worktree.removeIfIdle` is separate from ordinary `worktree.rm`. It never stops a terminal or chat, runs an archive hook, deletes a local branch, or falls back to recursive filesystem cleanup. Existing removal behavior is unchanged.

Check support with `orca worktree removal-capabilities --json`. The conditional method requires main-owned layout and sidebar presence, native local Git, a writable structured-session store, complete PTY and surface inventories, and exact workspace and physical Git identities. Folder, WSL, foreign-host, configured archive-hook, legacy window-owned layout, missing, partial and unknown inventories are refused. Client/server versions update independently: an unknown RPC method is unsupported, not permission to call ordinary removal.

Use `orca worktree rm-idle --request-id <uuid> --expect-json <json> --json`. The expectation is the `expected` object in `ConditionalWorktreeRemoval`: immutable instance and host identity, full worktree locator and repository, branch and HEAD, and canonical checkout/common-Git/admin-directory paths with device/inode identity. Do not reconstruct immutable identity from the pathname. Every active or restorable surface, pinned/main workspace, child workspace, changed identity, ignored/untracked file, Git operation or unpublished branch blocks removal. Business completion and ownership are the caller's responsibility and cannot be inferred from an idle checkout.

The host acquires a shared closing fence before verification. Terminal installs, structured create/attach, Git worktree creation and mutations, main-owned layout commands, user-view and phone-session registration, and legacy session snapshots participate in it. Earlier uses cause an immediate refusal without cancellation; later uses cannot enter the closing checkout. Existing structured records, including unreadable records, are conservatively retained.

A create-only `refs/orca-retained-worktrees/<request-id>` preserves the expected HEAD, and the local branch is kept. Request receipts live outside the checkout. A retry with the same request never removes the checkout again. If a prepared receipt proves the checkout and Git registration are already absent, the retry may finish metadata cleanup only for the same occupant, then requires final absence readback before marking the receipt removed. A replacement occupant is refused. An uncertain result stays refused until readback proves checkout and Git registration absent with the exact retained ref and branch. Do not change request identity to bypass uncertainty.

This method does not authorize closing unowned resources, adopting existing workspaces as automation-owned, deleting remote branches, merging reviews or publishing releases. Automation must separately track those conditions and keep the original ownership receipt. Native platform and mixed-version runtime validation are required before enabling automated execution.

The initial implementation refuses Windows hosts; physical-directory identity and receipt durability need platform validation there. Updating only a headless daemon is insufficient while it still uses legacy window-owned layout: the matching main-owned layout/sidebar build and its supported client protocol are prerequisites. Do not enable that product-wide layout switch as a side effect of installing this API.

The capabilities response describes the implementation/build prerequisites, not authorization to delete a particular workspace. Missing runtime stores, unreadable sessions, incomplete inventories, an active viewer, or unsupported clients still cause a per-request refusal. Closing admission canonicalizes filesystem aliases; unresolved paths are refused. External shells and editors outside Orca's managed session census are not an OS-level exclusion lock; automation must retain known external or unverifiable activity.

Initial Git admission is deliberately global to this runtime. Every non-read Git operation holds the guard, including explicitly routed and environment-routed Git commands. An earlier operation makes conditional removal busy; while one conditional removal is closing, later Git mutations in any repository are refused unless they carry that exact internal owner token. Conditional removals are serialized globally. This avoids guessing Git metadata routing and does not change ordinary Git behavior when no conditional removal is active.

File mutations are also conservatively serialized against conditional removal across this runtime. Runtime file commands, local filesystem provider mutations, legacy filesystem IPC, external upload streaming, and downloaded-file saving retain admission through asynchronous completion. A chunked download retains admission between requests until finish, cancellation, renderer loss, or expiry completes cleanup. Earlier mutations block removal; later mutations are refused before authorization or target resolution. Desktop view reports retain alias-aware admission until replacement, expiry, or disconnection. Ordinary file operations remain available when no conditional removal is closing.

Browser creation, paired-client opening, offscreen and renderer creation, recovery/adoption, restored-page publication and guest registration participate in admission. The create entry retains admission from before workspace resolution through asynchronous creation and publication. Detached layout publication and uncommitted client-page cleanup retain their own admission. A renderer create timeout or unverified client cleanup keeps conditional removal blocked for the rest of that runtime: a lost acknowledgement is not evidence that a late-created page is absent. Ordinary browser operations remain available without a closing conditional removal.

At-rest structured records, session snapshots and persisted surface maps are compared without rewriting their identities. Hosts must be proven equal before native physical directory identity is compared; a proven different host is separate. Unresolved paths, ambiguous snapshot hosts and unreadable inventories refuse removal. Saved unified tabs and sleeping-session records also retain a checkout.

Both initial success and receipt replay require checkout and Git-registration absence, exact retained ref and branch HEAD, and Orca occupant absence. Initial readback happens before the removed receipt is committed. Any disagreement or failed read leaves the prepared receipt and returns outcome_unknown. The caller still owns business completion, ownership and external-activity checks, and must perform the lifecycle's required absence readback before declaring cleanup complete; this API does not authorize cleanup from completion alone.

Reconciliation commands retain independent admission after dispatch. Action timeout, abort, reservation cancellation, lease fencing and the client-inventory grace deadline do not prove external absence. A successful restore/reclaim releases this admission only after local placement commit; a late success without that commit remains unknown. Exact completed close and protocol-defined failures with proven absence can release it. The executor-closed response can precede effects or follow successful cleanup of a partially created/rekeyed guest; failed cleanup returns cleanup_failed and remains held. Delivery failure, unknown results and unverified cleanup remain held without delaying the ordinary timeout/error response.

Session presence reads and persistence admission use one workspace/host target collector. More than 10,000 unique targets produce an incomplete inventory: reads remain unknown, while writes acquire global admission before saving. This keeps ordinary saves available without closing and protects unenumerated targets during the synchronous save boundary. It includes the merged active workspace key and its explicit execution host, falling back to the session partition only when that host is absent. Layout-owned unified tabs and sleeping records retain their existing main-owned write restrictions; collecting them at the persistence boundary does not make them writable by scalar window patches. Renderer requests release admission for proven pre-dispatch failures and exact replies, while send exceptions or timeouts with unknown external effects remain held.
