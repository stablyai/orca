# STA-3254 Windows Low reproduction

## Verdict

**Confirmed and fixed.** On Windows PowerShell 5.1, the WSL bridge prefix-bound Orca's documented `--for` flag to its own `ForwardArgs` parameter. Both documented wait conditions failed deterministically before the bridge invoked Orca, while the same argv reached a direct Windows target intact and the ticket's `--for=<value>` workaround crossed the bridge intact.

## Ticket context

The full coordinator-provided Linear export describes Orca 1.4.164 on WSL2 Ubuntu through Windows PowerShell 5.1. The original report says `terminal wait --for tui-idle` fails because `--for` is treated as an abbreviation of `ForwardArgs`; it links GitHub issue [#12196](https://github.com/stablyai/orca/issues/12196), relates STA-2171 and STA-3266, and records `--for=tui-idle` as the workaround.

STA-3266 is a distinct later-stage failure: it concerns native argv construction after the bridge body reaches `& $OrcaLauncher @ForwardArgs`. STA-3254 fails earlier, during the bridge script's own parameter binding.

## Reproduction boundary

This Windows profile had no live Orca runtime and no registered WSL command: `~/.local/bin/orca-ide` and `~/.local/share/orca/orca-wsl-bridge.ps1` were absent, and `wsl-cli-registrations.json` reported no registered distros. I therefore used a disposable launcher plus the exact bridge generated by `buildWslBridgeScript()` and exercised it across the real Ubuntu WSL -> `powershell.exe -File` boundary.

The disposable bridge matched the checkout-generated bridge after only CRLF/LF normalization (`sha256 28fa60ed69579608686e332d579606903a332834f93db68840a2eddfaf7886e7`). One launcher targeted an argv-dump PowerShell script; the other targeted the installed native `resources/bin/orca.exe`.

## Commands tested

Representative documented forms:

```text
orca terminal wait --terminal term_example --for tui-idle --timeout-ms 60000 --json
orca terminal wait --terminal term_example --for exit --timeout-ms 60000 --json
```

The first form appears repeatedly in `skill-guides/orchestration.md`; the second is the example in `src/cli/help.ts`. I also tested a non-`--for` control and the ticket workaround.

## Forwarded argv evidence

| Invocation | WSL bridge result | Direct Windows result |
|---|---|---|
| `terminal show --terminal term_example --json` | Exit 0; forwarded `['terminal','show','--terminal','term_example','--json']` | Exit 0; identical five entries |
| `terminal wait --terminal term_example --for tui-idle --timeout-ms 60000 --json` | Exit 1; target never invoked, so no argv was forwarded | Exit 0; all nine entries preserved, including separate `--for`, `tui-idle` |
| `terminal wait --terminal term_example --for exit --timeout-ms 60000 --json` | Exit 1; target never invoked, so no argv was forwarded | Exit 0; all nine entries preserved, including separate `--for`, `exit` |
| `terminal wait --terminal term_example --for=tui-idle --timeout-ms 60000 --json` | Exit 0; all eight entries preserved | Exit 0; identical eight entries |

Both spaced WSL cases returned:

```text
A positional parameter cannot be found that accepts argument 'terminal'.
FullyQualifiedErrorId : PositionalParameterNotFound,orca-wsl-bridge.ps1
```

The bridge body and argv-dump target did not execute in either failing case.

## Actual Orca CLI comparison

Using the installed native CLI as the bridge target produced the same split:

| Path | Form | Result |
|---|---|---|
| WSL bridge -> installed CLI | `--for tui-idle` | PowerShell `PositionalParameterNotFound`; Orca never ran |
| WSL bridge -> installed CLI | `--for=tui-idle` | Reached Orca; Orca then reported `runtime_unavailable` because the desktop runtime was offline |
| Direct Windows installed CLI | `--for tui-idle` | Reached Orca; same expected `runtime_unavailable` |
| Direct Windows installed CLI | `--for=tui-idle` | Reached Orca; same expected `runtime_unavailable` |

The offline runtime limits end-to-end terminal waiting, but it strengthens the stage isolation: direct Windows and equals-form WSL calls both reach the same Orca runtime lookup, while spaced-form WSL calls die in PowerShell first.

## Diagnosis

The generated bridge is an advanced PowerShell script:

```powershell
[CmdletBinding(PositionalBinding=$false)]
param(
  [Parameter(Mandatory=$true, Position=0)]
  [string]$OrcaLauncher,
  [string]$WslCwd,
  [Parameter(ValueFromRemainingArguments=$true)]
  [string[]]$ForwardArgs
)
```

Windows PowerShell permits unambiguous parameter-name prefixes. During `-File` binding it interprets Orca's `--for` token as the bridge parameter `ForwardArgs`, consuming the following wait condition as that parameter's value. The earlier ordinary tokens such as `terminal` can no longer bind under `PositionalBinding=$false`, so binding raises `PositionalParameterNotFound` before the script enters its `try` block or calls the native launcher.

`--for=tui-idle` stays one argument and is not prefix-bound, which explains the documented workaround. Direct Windows invocation has no outer bridge parameter binder, so `--for` and its value remain separate argv entries for Orca.

## Coverage observation

Before the fix, `src/main/cli/wsl-cli-installer.test.ts` asserted the generated parameter block and native invocation text but did not execute Windows PowerShell 5.1 with a colliding CLI flag. Separately, `src/cli/index.test.ts` covers direct CLI parsing of `terminal wait --for tui-idle`; that path cannot expose the WSL bridge collision.

## Fix validation

The bridge now reads its three launcher-controlled header arguments from PowerShell's automatic `$args` array instead of declaring a parameter block. Forwarded argv begins at the next fixed index, so PowerShell has no bridge parameters against which it can prefix-bind Orca flags.

Focused coverage verifies both generated scripts and the real `powershell.exe -File` boundary. On Windows PowerShell 5.1.26100.8875, the fixed generated bridge forwarded the exact ordered argv, including separate `--for`, prefixes of the former `WslCwd` and `OrcaLauncher` parameters, and a literal `--`.

The bash launcher still forwards with `"$@"`, and the bridge still invokes the target with `@ForwardArgs`. The fix deliberately does not rebuild or requote native argv, leaving STA-3266's later quote-preservation concern separate.

## Final assessment

STA-3254 was a deterministic WSL bridge defect, not an Orca CLI parser defect and not STA-3266's quote-forwarding defect. Removing the bridge parameter-binding stage restores the documented spaced `terminal wait --for exit|tui-idle` forms without changing the later native argv handoff.
