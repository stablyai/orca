⏺ Separate badge it is. I have no more blocking questions — here's the short
  design for approval:

  Design: PR review threads in local worktree diff views (read-only)

  Data source — reuse, don't refetch. A new hook
  useLocalPRReviewThreads(worktreeId) resolves the worktree's linked GitHub PR
  (already tracked by the hosted-review store, including the PR's headSha) and
  reads the review threads from the same module-level workItemDetailsCache the
  PR page uses (useSyncExternalStore + the existing SWR fetch, 30s freshness).
  No linked PR → the hook returns nothing and fetches nothing. GitHub only;
  GitLab/Bitbucket untouched.

  Anchoring — three-tier check, drifted threads go to the outdated group:
  1. Thread already marked outdated by GitHub → outdated group.
  2. Local HEAD == PR headSha and the file has no uncommitted changes → render
     inline at the recorded line (exact by construction).
  3. Otherwise, compare the thread's anchor-line content against the local file
     at that line. For this I'll add one field to the existing GraphQL threads
     query — diffHunk on the root comment (its last line is the anchor line's
     content) — mapped onto PRComment. Match → inline; mismatch → outdated
     group. LEFT-side (deleted-line) threads always go to the outdated group,
     since the local diff's left pane is the merge-base, not the PR base.

  Rendering — existing components, no actions passed:
  - Per-file committed diff (DiffViewer.tsx, diffSource: 'branch'): PR threads
    are appended to the comment decorator's list as the same
    DecoratedDiffComment+reviewThread shape the PR page uses. With no action
    callbacks, ReviewThreadCard already renders read-only (no reply box, no
    resolve button — covered by an existing test). A read-only
    OutdatedThreadsGroup renders below the diff.
  - "View all" (combined-branch → CombinedDiffViewer/DiffSectionItem): same
    thread items passed through the props I added for the PR page, actions
    omitted; outdated group per file section.
  - Resolved threads behave like on the PR page: collapsed to one row, click to
    expand.

  Source control badge: branch-section rows (list + tree view) get a second,
  visually distinct badge — comment icon + count, muted — from a
  prThreadCountByPath map, alongside the existing local-notes count.

  Testing: unit tests for the anchoring function (all three tiers + LEFT-side),
  hook test for cache-read/count-map, a DiffViewer test asserting threads render
  without write affordances, and a badge rendering test. Then
  lint/typecheck/localization gates as usual.

  Out of scope: uncommitted-changes diffs (staged/unstaged), any write actions
  from local views, non-GitHub providers.

  Roughly 5 new files + 6 modified, well within existing patterns. Approve, and
  I'll implement (still nothing committed — everything stays in the working
  tree)?

❯ how the fetch of the new comments works? Is there an interval where is        
  downloading or is workign in other way?                                       

⏺ Short answer: there's no polling interval — it's fetch-on-demand with a shared
  cache (stale-while-revalidate). Here's the exact flow:

  1. Trigger. The hook (use-local-pr-review-threads.ts) fetches when a surface
     that needs comments mounts or its identity changes — opening a "Committed
     on Branch" file diff, opening "View all", or the source control panel
     rendering the branch section (for badges). No timer runs in the background.
  2. Freshness gate. Before fetching it checks the shared cache (the same
     workItemDetailsCache the PR page uses): an entry younger than 30 seconds or
     a fetch already in flight → no network call at all. Older → one background
     refetch while the cached comments keep rendering (stale-while-revalidate).
  3. Under the hood it's one gh CLI round trip (GraphQL for threads + REST for
     the rest), and gh itself applies its own 60-second HTTP cache to the REST
     parts — so rapid open/close cycles cost almost nothing against your rate
     limit.
  4. Shared + reactive. Because the cache is shared and subscribed via
     useSyncExternalStore, any surface writing fresh data updates all the others
     instantly — e.g., open the PR page and the branch-diff threads/badges
     re-render from the same fetch.

  So new comments appear when you re-enter the surface (switch file tabs, reopen
  View all, toggle the panel) and it's been >30s — not while you sit motionless
  on an open diff.
