Terminal reattach fast path

Every time you switch workspaces, each terminal pane re-saves the entire 9.2 MB app state — even when nothing changed. This design adds a cheap “already saved?” check that skips all that work. No product code changed yet; this page is the whole spec, visualized.

The problem: paying for a save that saves nothing

Mounting or remounting a terminal pane calls Store.persistPtyBinding. Today that path clones the session → mutates → flushOrThrow → serializes everything → hashes → usually skips the disk write. The disk write is skipped, but the expensive serialization already happened.

The key mental image: the main thread is a single checkout lane. Serialization is a customer with a full cart who, at the till, is told “you already paid” — but everyone behind them (your keystroke) still waited. The fix is to check the receipt before unloading the cart.

Why it fires constantly: the cold-park policy

The renderer keeps at most 4 workspaces and 6 tabs warm (terminal-hidden-view-parking.ts). On a many-worktree install, nearly every workspace switch remounts every pane — and each pane reattaches.

� parking-garage analogy — Only 4 cars fit in the heated garage; the rest park outside in the cold. Every time you want a cold car, you rebuild the entire garage inventory from scratch just to confirm your car is still where you left it. The fast path is glancing at the parking ticket instead.

The change: one early return, in exactly the right slot

Add an early return to persistPtyBinding (loading-store/pty-binding-persistence.ts) that fires when the binding is already in memory and already on disk. Nothing is cloned, nothing serialized on that path. It returns true — which matters (see below).

The no-op predicate: 9 locks, one key

All nine must hold. Any miss falls through to the existing code unchanged — the fast path only ever skips work it can prove is redundant. Click each row for the reasoning. Progress: 0 / 9 verified

✓
args.expectedSourceBinding === undefined
Split path always changes membership + arms the topology fence.
🔀 If a split is in flight, layout membership is about to change by definition. Skipping the flush would skip the fence bump that invalidates stale readers. So: any split intent → fall through, always.
✓
isTerminalLeafId(args.leafId)
Legacy leaf ids take a different early-flush branch that never writes layout state.
🧬 Legacy ids have their own semantics. The fast path only understands the modern terminal-leaf shape; anything else → existing code.
✓
tab exists, tab.id === args.tabId, tab.ptyId === args.ptyId
Otherwise the call would mint a new tab — real state change.
➕ The normal path creates the tab row if missing or repoints it. If we skipped that, the tab would silently never exist. Existence + exact PTY match required.
✓
layout exists, layout.root ≠ null, layoutContainsLeafId(root, leafId)
Otherwise the call would mint or split the layout.
🌳 The pane must already be a member of the tab's layout tree. A missing layout or a leaf that isn't in the tree means the write path would restructure — not a no-op.
✓
layout.ptyIdsByLeafId[leafId] === args.ptyId ⭐ the load-bearing binding
The actual “this pane shows this PTY” fact. Everything else is scaffolding around this one equality.
🔑 This is the core claim: the requested binding already is the stored binding. All other conditions exist to make sure “stored” also means “complete, live, and durable”.
✓
incarnations[paneKey] === args.incarnationId (strict)
undefined === undefined matches; defined-vs-undefined does not.
🔄 The incarnation distinguishes “same PTY, fresh spawn” from “same PTY, same process”. Strict equality closes the hole where a respawned pane could masquerade as the old one. Tests 3–4 pin both directions.
✓
expectedBinding === undefined || expectedBinding.incarnationId === incarnationId
A reconciled incarnation must still bump the topology fence.
🚧 Even when the PTY matches, a reconcile event carries ordering information (the fence) that downstream readers use. Skipping it would freeze the revision — so reconcile → fall through and bump. Test 6 pins this.
✓
!tombstones[paneKey]
The write path clears tombstones — that clearing is itself a state change.
🪦 A tombstone means “this surface was retired”. The normal write consumes it. Skipping would leave a stale retirement marker behind. Test 5 seeds a tombstone from a data file to pin this.
✓
Binding is durable — lastDurableWriteGeneration ≥ writeGeneration
In-memory equality can match a binding still waiting in the debounced save. Memory ≠ disk.
💾 The generation counter (next section) proves the bytes are actually on disk — or proven byte-identical by hash. Without this, a crash window opens: we'd report “saved” for state only in RAM.
5

Durability check: two counters, one inequality

Two generation counters replace any need for timer or in-flight checks. The rule is one line: runtime.lastDurableWriteGeneration >= runtime.writeGeneration.

Interactive — drive the counters

writeGeneration (dirty — work requested)

lastDurableWriteGeneration (safe — bytes on disk / hash-proven)

Fast path allowed? YES — durable ✓

W=4 D=4 — in sync.

Lifecycle rules (why no timer check is needed)

EventWDEffect
scheduleSave+1 first—any scheduled write opens a gap D < W by construction
writeToDiskAsync—raise after durable rename / hash-proofgap closes only when bytes are proven
in-flight / failed write—untouchedD stays behind → fast path correctly refuses
The invariant does the work: a scheduled, in-flight, or failed write always leaves D behind W, so the single inequality detects all three. No separate “is a save pending?” flag can drift.
Scope note: the check asks only “is this binding on disk?” Unrelated dirty state keeps its own save and its own crash window — skipping this flush never widens it.
6

The one-line companion fix: the parked counter

writeToDiskSync raises D only after a real rename. On a hash match (state unchanged, write skipped) it returns without touching D — while flushOrThrow already bumped W. The counter parks one behind forever, and the fast path would stay disabled.

Without the fix — fast path disables itself 
W=5 D=4   ← sync flush, hash match, no rename
            D untouched → gap never heals
            (debounce timer also cleared → nothing reschedules)

next reattach:  D(4) < W(5) → fall through
                → flush again → hash match again → W=6 D=4
                → …disabled forever ♾️
With the fix — one line 
on unforced hash-match return:
  lastDurableWriteGeneration =
    max(lastDurableWriteGeneration, writeGeneration)

A matching hash proves the file already holds this state — exactly what D records. Mirrors the async branch. The force path is deliberately excluded: it exists because an async rename may be racing past the generation check, so contents are not yet proven. Failed writes never raise D.

PtyBindingPersistenceOperationsRuntime widens from Pick<…,'flushOrThrow'|'state'> to also include writeGeneration, lastDurableWriteGeneration. No new tracking state.

⚠️ Named behavior delta for the PR: a no-op reattach after the quit flush has started currently throws from flushOrThrow (and spawn-commit-persist.ts tears down the fresh spawn). With the fast path it returns true — correct, because the binding is durable.

Verification: reproduce first, claim later

⚠ Before implementing — re-run the probe

Live capture proved memory matched, but not whether a save was pending. A workspace switch sends a renderer session patch → scheduleSave before panes remount — so the first reattach per burst may legitimately flush the patch; only later panes hit the fast path.

Probe now records per call: savePending writeGeneration lastDurableWriteGeneration (config/scripts/persistence-call-probe.mjs).

If every captured call shows a pending save, fix 1 alone does not move the number — the renderer's switch-time patch cadence becomes the next target.
✔ After — measure on the real install 
pnpm tc:node
pnpm test src/main/persistence-flush-and-save-scheduling.test.ts \
  src/main/persistence/loading-store
# + the eleven real-store files

Target: zero buildStateToSave calls with persistPtyBinding on the stack during parked-workspace switches, where savePending was false. Then a typing capture (capture-live-input-lag.mjs) reporting queue-delay distribution before/after.

Do not claim the lag is fixed from persistence numbers alone — the unattributed remainder of the 117 ms needs its own capture.

Deferred: fixes 2 & 3 (constraints recorded, not lost)

Fix 2 · Small binding transactions

Persist only recovery-critical binding state, not the whole document

The session clone exists only for restoreSession after failed flush — a narrow rollback must restore tab row + layout + incarnation + tombstones + topology revision. If bindings leave the single document, every consumer must follow:

ConsumerWhat breaks
backup-recovery-rotation.tsbackup rotation + .bak recovery
ssh/orcad-state-snapshot.tscopies profiles/ wholesale on remote hosts
profile transfer / move, downgradeolder builds read orca-data.json directly → boot with no bindings
Fix 3 · Off-main serialization

Move stringify off the main thread (autosave path only)

The debounced autosave still serializes synchronously before its first fs await. Three hard constraints:

#Constraint
🔐Secret encryption uses Electron safeStorage → must stay on main. Only stringify / sentinel substitution / encoding / hashing can move.
🪞Worktree-meta projection settles rows on reference identity — a structured-clone boundary destroys it.
🚧flushOrThrow is a synchronous barrier (binding, retirement, credit ledger, quit) — a worker can't provide it. Converting every caller is its own change + crash-window analysis.
🧭 The big picture — Fix 1 (this spec): stop doing redundant work · Fix 2: make necessary work smaller · Fix 3: move remaining work off the main thread. In that order, because each later fix has a wider blast radius.
